# santekno/sdk gaps

The API uses [santekno/sdk](https://github.com/santekno/sdk) for every concern it covers. This file lists what the sdk does not cover (yet), where an sdk package exists but does not fit (each such row says why, as for `apikey`), and what GoShop does instead. Each gap is a candidate for an upstream sdk contribution.

GoShop pins **sdk v0.2.0, released 2026-10-22 (tag v0.2.0, commit 97a873a)**, from [PR #33](https://github.com/santekno/sdk/pull/33): the first version with `middleware/chi`, `uuidx.NewV7`, and the `healthx` JSON `Content-Type` fix plus `Handler.HideErrors`. Always pin `@v0.2.0` explicitly, never `@latest`.

| Concern | Gap in sdk | What GoShop does | Since |
|---|---|---|---|
| chi middleware, UUIDv7, health probe JSON | Missing in v0.1.8. | Resolved in v0.2.0; pin `github.com/santekno/sdk v0.2.0`, no adapter needed. | Bab 2 |
| Config parsing | `configx` typed getters (`Int`, `Duration`) return 0 for a malformed value instead of an error, and `WithEnv` reads only the process environment under one prefix, so Railway's unprefixed `PORT` is outside it. | `internal/config` reads values as strings, parses and range-checks them itself, reads `PORT` with `os.LookupEnv`, and joins every problem into one startup error. | Bab 2 |
| CORS | sdk has no CORS middleware. | [`github.com/go-chi/cors`](https://github.com/go-chi/cors) in `internal/httpserver`, origins from `APP_CORS_ALLOWED_ORIGINS`. It treats an empty origin list as "allow all", so GoShop passes a deny-all `AllowOriginFunc` when the list is empty. | Bab 2 |
| Request timeout | `middleware/chi` has no timeout middleware, and chi's `middleware.Timeout` answers with a bare 504 (no body). | `httpapi.Timeout`: a context deadline per request, and 503 `TIMEOUT` through `DefaultErrorWriter` when the handler wrote nothing. | Bab 2 |
| Request-scoped log fields | `logx.Logger.WithContext` only adds fields from registered extractors, and logx registers none, so the request ID set by `RequestID` is not added on its own. | `internal/logging` registers extractors for `ctxx.RequestID` and `ctxx.UserID` at init, and its middleware stores a per-request logger with `logx.WithContextLogger`. | Bab 2 |
| Validation errors over HTTP | `validx.Validator` returns go-playground's raw `ValidationErrors` (Go field names, no messages), does not expose `RegisterTagNameFunc`, and has no query binder. | `httpapi.Validator` decodes `query`-tagged structs, names top-level fields by their `query`/`json` tag, writes one short message per field, and returns a 400 `VALIDATION_FAILED` `errx.AppError`. **Limitation:** a field inside a nested struct (or promoted from an embedded one) is reported by its Go name (`City`, not `address.city`), with a message from the failed rule alone (no combined "between"), and two nested fields with the same Go name share one key; only top-level fields use their tags. Nested body paths arrive with the chapter that first sends a nested body. The real fix is a validx option for `RegisterTagNameFunc` (candidate sdk contribution). | Bab 2 |
| Migrations | sdk has no migration runner. | golang-migrate (v4.20.1): its CLI for `make migrate-*`, and its library with the migrations embedded in the binary for `api migrate` (the Compose `migrate` service, Railway's pre-deploy command). | Bab 3 |
| Array parameters | sqlc's `database/sql` output wraps every array parameter in `pq.Array` from `github.com/lib/pq`; nothing in pgx's `stdlib` takes its place in generated code. | `lib/pq` is a dependency for `pq.Array` only. The connections stay pgx's: `pq.Array` turns the slice into a Postgres array literal, which pgx sends as the parameter. | Bab 3 |
| Transactions | `sqlx` has no transaction helper. | `database.WithTx(ctx, db, fn)`: begins a transaction, hands `fn` the sqlc queries bound to it, commits on `nil`, rolls back on an error or a panic. | Bab 3 |
| S3 storage | `storagex` has only `MemStorage` and `LocalStorage`: no S3 and no presigned URLs. | GoShop's own S3 adapter implementing `storagex.Storage`, with presigned upload URLs, works against SeaweedFS locally and any S3-compatible bucket in production. | Bab 6 |
| Rate limiting | `ratelimitx` is a nested module with its own `go.mod` (`github.com/santekno/sdk/ratelimitx`) and no `ratelimitx/vX.Y.Z` tag, so the root tag does not include it. Its `Client` interface (`Incr`, `Expire`, `PTTL` returning values) does not match go-redis, whose methods return command objects. When the `Expire` after the first `INCR` fails, `Allow` ignores the error: that window's key then has no TTL and stays in Redis for good (a slow memory leak), and once it is over the limit, `PTTL` finds no TTL and `RetryAfter` falls back to the full window. It is no lasting lockout: the key carries the window's start time, so the next window counts on a new key. `RetryAfter` also overstates the wait by up to one window: the windows are aligned (`bucketID` uses `now.Truncate(window)`), but the key's TTL is a full window from the first attempt, and `RetryAfter` is that TTL. A first attempt at 09:06 in a 15-minute window is told `Retry-After: 900` (09:21) although a new window starts at 09:15. | Pinned by pseudo-version **`v0.0.0-20261022004014-97a873a6fbad`** (sdk `main` at commit 97a873a, the v0.2.0 commit), never by `replace`; switch to a tag once one exists. `internal/redisconn.Counter` adapts go-redis to `ratelimitx.Client`. `auth.RedisRateLimiter.Allow` sends the smaller of ratelimitx's `RetryAfter` and the time until the aligned window ends (`window - now.Sub(now.Truncate(window))`), with one clock shared with ratelimitx through `WithNow` (Bab 5). The swallowed `Expire` error is accepted for Bab 4 (it needs Redis to fail between two commands of one request, and costs one stray key) and is a candidate fix upstream (`INCR` + `EXPIRE NX` in one pipeline, or return the error). | Bab 4 |
| Redis client | `redisx.RedisClient` says go-redis v9 "satisfies this interface out of the box", but go-redis's `Get`, `Set`, `Del` and `SetNX` return `*StringCmd`/`*StatusCmd`/…, not `(value, error)`, so it does not compile. redisx also has no ping for health checks. | `internal/redisconn.KV` adapts go-redis to `redisx.RedisClient` (mapping `redis.Nil` to `redisx.ErrKeyNotFound`), and `redisconn.Pinger` to `healthx.Pinger` for the `redis` readiness check. go-redis v9.23.0 itself is the client. | Bab 4 |
| JWT claims | `jwtx.Verify` checks the signature, the algorithm (pinned by the key; `alg=none` refused) and `exp`/`nbf` when present, but accepts a token **without** `exp`, never checks `iss` or `aud`, and compares times with the wall clock (its `nowFunc` is unexported, so there is no clock option and no leeway). | `auth.AccessTokens.Check` requires `exp`, `iat`, `sub`, `jti`, `sid`, a known `role`, `iss = goshop-api` and `aud ∋ goshop`, and checks expiry again with the API's injectable clock. Tests may move that clock forward, never back (jwtx would refuse the new tokens). Candidate upstream: `VerifyOptions{Issuer, Audience, Now, Leeway, RequireExp}`. | Bab 4 |
| JWT middleware | `middleware/chi` `JWTAuth` answers every failure with the same 401 `UNAUTHORIZED` (an expired token cannot be told from a forged one), sets no `WWW-Authenticate`, and has no hook for extra claim checks or a revocation lookup. | `auth.Guard` wraps it: `WithErrorWriter` adds `WWW-Authenticate: Bearer` and the API's error path, then a second step runs `AccessTokens.Check` and the Redis session-revocation lookup. The contract documents that clients refresh on any 401. | Bab 4 |
| Password hashing | `hashx.HashPassword` uses fixed argon2id parameters (64 MiB, t=3, p=4) with no option to change them and no limit on concurrent hashes, so a burst of logins can use 64 MiB each. | `auth.Argon2Hasher` runs at most four hashes at once per instance (a semaphore that honours the request's context) and keeps hashx's parameters, which are encoded in each hash. It also verifies against a dummy hash for unknown users so login timing reveals nothing. | Bab 4 |
| OIDC / Google sign-in | sdk has no OpenID Connect or Google ID-token verifier. | [`github.com/coreos/go-oidc/v3`](https://github.com/coreos/go-oidc) v3.21.0 (`oidc.NewVerifier` with Google's JWKS, no discovery call at start), behind GoShop's `auth.GoogleVerifier` interface. Chosen over `google.golang.org/api/idtoken` for its small dependency tree (go-jose, x/oauth2) and its clock option. | Bab 4 |
| Opaque tokens | `apikey` (`Generate`, `HashKey`, `Verify`) makes and checks random keys, but it is shaped for API keys: it finds a key by the SHA-256 of the whole key (`HashKey` "to look up a key by its hash"), with no row id in the key; its random part is 24 bytes (`RandomLen`, 192 bits); it reads `crypto/rand` directly, so a test cannot pass its own source; and it returns the hash as 64 hex characters. | `internal/auth/opaque.go` makes refresh, verification and reset tokens as `<row id>.<32 random bytes>` (256 bits) from an injectable `io.Reader`, stores the SHA-256 as 32 bytes (`bytea`, with a length CHECK), finds the row by its id and compares the hashes with `hashx.ConstantTimeEqual`. Candidate upstream: a reader option and an id-carrying variant. | Bab 4 |
| Email | sdk has no mailer. | `internal/mail.Mailer` with a logging implementation in Bab 4; SMTP from the worker in Bab 6. | Bab 4 |
| Test databases | `testx.PostgresContainer` and `testx.RedisContainer` start nothing: they read `POSTGRES_DSN` / `REDIS_ADDR` and call `t.Skip` when unset (`RedisContainer` also skips when it cannot connect). | `make test-integration` starts the Compose dependencies, exports `POSTGRES_DSN`, `REDIS_ADDR` and `S3_ENDPOINT`, and fails if any test was skipped (`scripts/no-skips.sh`). From Bab 3 the integration tests use `POSTGRES_DSN` only to reach the server: each test creates its own migrated `it_<random>` database and drops it `WITH (FORCE)` afterwards (`tests/integration/db_test.go`), so the seeded `goshop` database is never written to and tests may count rows. | Bab 2 |
| SQL pool settings | `sqlx.Config` treats `0` as "use the default" for `MaxOpenConns`, `MaxIdleConns` and `ConnMaxLifetime` (25, 5, 5m), so "no idle connections" cannot be configured, and it has no `ConnMaxIdleTime`. | `internal/config` requires `1` or more for both connection counts and passes all three explicitly. Nothing else needed. | Bab 3 |
| HTTP client JSON helpers | `httpx.Client` fits (timeout, circuit breaker, retries only for idempotent methods), but `PostJSON`/`GetJSON` decode the answer with no size limit, put up to 4 KiB of an error answer's body into the error text, and `WithAPIKey`/`WithBearerToken` prefix the key (`ApiKey `, `Bearer `) where Biteship wants it bare. | `shipping.Biteship` builds its request and calls `httpx.Client.Do` (timeout `APP_SHIPPING_TIMEOUT`, `WithRetries(0)`, the key through `WithDefaultHeader("Authorization", …)`), checks the status itself, and decodes at most 1 MiB through `io.LimitReader`; an error answer's body is never read into a message. Candidate upstream: a response size limit option and a typed status error without the body. | Bab 5 |
| HTTP client circuit breaker | `httpx.Client.Do` counts every transport error as a breaker failure, the caller's own cancellation (`context.Canceled`) included. Five requests whose clients hung up open the breaker for 30 s, for every caller of that client. | `shipping.Biteship` calls `Do` with `context.WithoutCancel(ctx)`, bounded by its own `APP_SHIPPING_TIMEOUT`, so a buyer hanging up never counts against Biteship. Candidate upstream: do not record `context.Canceled` (and a caller's deadline) as a failure. | Bab 5 |
| Domain events | sdk has no outbox, job queue or event publisher (`messagingx` is a chat provider for Telegram, not a message bus). | `internal/outbox`: `Record` writes an event in the caller's transaction, `Dispatcher.PublishPending` claims batches with `FOR UPDATE SKIP LOCKED` and hands them to a `Publisher`; `LogPublisher` in Bab 5, the worker's queue in Bab 6. | Bab 5 |
| Tracing, metrics | `tracex` is an interface with a no-op tracer only; `metricx` is an interface with an in-memory registry only. Neither exports anywhere. | OpenTelemetry and Prometheus adapters implementing the sdk interfaces. | Bab 19 |
